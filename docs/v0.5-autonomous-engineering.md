# v0.5 — evidence-driven candidate selection

**Status: in development.** Not released; the package stays at 0.4.0 until the v0.5 live acceptance passes. This document is
the design as it is built, kept current as each part lands (see [Delivery plan](#delivery-plan)).

**Models propose. Fusion verifies. Humans approve.** v0.5 extends that thesis: models may propose several competing
solutions, but no model selects the winner. Fusion materializes every candidate in its own private workspace and holds all of
them to one verification profile, frozen before any result exists. It runs its own experiments to tell them apart and selects
only when its own evidence justifies it. When it cannot, it says so: a tie is a human decision, not a model's.

What Fusion can say about a selection:

> Candidate c2 was selected because c1 failed obligation X, and c2 passed the frozen verification profile and its fresh
> revalidation.

What it never says: "a model preferred c2", "two models voted for c2", "c2 looked cleaner", "c2 scored 91%".

## The flow

```text
problem
→ frozen task contract and evidence snapshot (the baseline reproduction, a checked finding's basis)
→ the verification profile, frozen and hashed before any candidate exists
→ independent candidates: the same frozen contract, each its own brief, context, view and private workspace
→ host materialization (Fusion applies each proposal; the primary checkout stays untouched)
→ the common profile for every candidate
→ Fusion's experiments (probes, property and fuzz runs, mutations of each candidate's own change)
→ falsification where the policy requires it
→ elimination and evidence dominance — or an explicit tie
→ fresh reconstruction and revalidation of the selected candidate
→ the v0.4 delivery → your approval → the checkout-bound apply
```

## Routing — when a tournament runs (`src/core/tournament/route.ts`)

Not every task starts several candidates. The policy is host-owned, versioned code (`v0.5-route-1`), never learned online:

- Read-only work and critical tasks are never tournaments. A critical task stops at the human gate before any candidate exists.
- A task is **eligible** when there is something to compare: risk at least medium, a security-sensitive task, a diagnosis
  with competing explanations, or an earlier failed attempt at the same task.
- An eligible **fix or refactor** runs **2 candidates** by default. A plain change (a feature) stays single unless you ask.
- **You** may ask for 1–3 candidates. More is refused as over budget, before any model turn.
- A **model's advice** is recorded as advice. It may start the default tournament for an eligible task the policy would keep
  single. It can never add candidates, never apply to an ineligible task, and never lower what the policy chose.

## Candidates (`src/core/tournament/contracts.ts`, `strategies.ts`)

A candidate's lifecycle is typed state that only Fusion advances:

```text
proposed → materialized → verified | unverified | rejected | failed
verified → survivor | rejected
survivor → selected | notSelected | tied
tied → selected | notSelected        (your choice)
selected → revalidated | rejected    (a revalidation mismatch)
revalidated → deliveryEligible
```

Any other transition is an error; none is inferred from a model's words. A candidate cannot move itself to *selected*.

Every candidate author receives the same frozen task contract plus one Fusion-authored **strategy brief**:
- c1: the most direct fix;
- c2: the underlying cause;
- c3: a sound alternative where one exists.

A brief never names or hints at a winner, and each allows the sound fix when no real alternative exists. Candidates see
nothing of each other: no proposal, reasoning, patch or result. Fusion records how independent generation really was — only
separate contexts, or also separate provider bindings or models — and never claims model diversity for separate contexts
alone. Candidates that make the identical change **converge**. That is recorded as information and is never proof.

## The frozen verification profile (`src/core/tournament/profile.ts`)

Before the first candidate exists, Fusion freezes the common profile and records its SHA-256. It contains:
- the configured confined checks;
- what the baseline reproduction showed (the checks that must go from failing to passing);
- the proof obligations of the v0.4 reliability policy;
- whether falsification is required;
- the repository's configured experiments.

A candidate-specific addition, such as Fusion's mutations of that candidate's own change, may only add checks. A collision with
a common check is refused, and there is no way to express a removal.

## The verification mesh (`src/core/tournament/mesh.ts`)

Every proof channel a candidate faced is a node, bound to that candidate's exact revision (its manifest's SHA-256). A node
records:
- what ran and who defined it;
- whether its authority is deterministic (Fusion ran it) or a model's (advice only);
- its host-observed result and the digest of its output;
- the obligation it bears on.

The mesh adds no second truth system. Its deterministic pass/fail nodes enter the v0.4 evidence decision as more
verification checks:
- an experiment that fails, fails `verificationPassed`;
- one that did not run leaves the verification incomplete, which never passes;
- a model saying "the property tests pass" creates no node at all.

## Experiments Fusion runs

- **Probes** (configured by the repository owner), with a host-owned expectation:
  - `baseline` — a preservation condition: outside the fix, the candidate must behave exactly like the unchanged baseline
    (exit code and output digest);
  - `output` — an explicit oracle (exit code and, optionally, the exact output);
  - `compare` — no oracle. A difference between candidates discriminates but eliminates no one.

  A truncated output is never compared; Fusion does not fabricate precision.
- **Property and fuzz runs** of the repository's own harness, with a deterministic seed and a bounded number of cases
  appended by Fusion. A failing case is kept as a bounded, redacted reproducer that can be replayed exactly.
- **Mutations** (`src/core/tournament/mutation.ts`). Fusion, never a model, reverts one changed region of one non-test file
  of a candidate's own change and verifies the result against the common checks.
  - A mutation the checks detect is killed.
  - One they do not detect *survived*: an evidence weakness of that candidate, not a failure.
  - Test files are never mutated, and neither are created files or files larger than the diff bound. Fusion says which
    files it did not mutate.

Every experiment has hard limits, which models cannot change:
- at most 4 probes, 2 property runs and 2 fuzz runs — together at most 8 commands, the bound of one confined run;
- at most 200 property cases and 500 fuzz cases per run;
- at most 3 mutations per candidate;
- one experiment batch per tournament.

### How Fusion runs them (`src/app/tournament/experiments.ts`)

- **Never on the host.** Every experiment is a confined verification through the same port, backend and refusals as the
  common checks. A refusal leaves the experiments unrun; it is not retried.
- **On a candidate Fusion materializes itself.** Fusion takes a fresh private candidate from the committed baseline and
  applies the candidate's exact host ChangeSet. The application ledger must hash to the one the candidate was judged on.
  - A different tree is a security violation (`CANDIDATE_SECURITY_VIOLATION`), never a silently different candidate.
  - So is a workspace handle outside the private candidate root.
  - Every materialization is released, even when the backend throws, and its cleanup report is kept.
- **Each experiment exactly once.** A confined run stops at its first failing command. Fusion continues with the commands
  that did not run, on a new materialization, so one failing probe cannot hide the others.
- **Honest results.**
  - A timeout or a spawn failure detects nothing: the experiment stays unrun, never passed or failed.
  - A mutation counts as killed only when a check ran and failed.
  - Outputs are compared by digest, and only when the backend retained them completely (the Docker backend keeps the last
    8 KiB of each command's output).
- **Replayable counterexamples.** Property and fuzz runs get a seed derived from the frozen profile's hash and the
  experiment's id: the same for the baseline and every candidate, and different when the profile changes. A failing run
  is kept as its replay recipe: the experiment, the seed, the case count and a bounded excerpt. The excerpt is held in
  memory and persisted only through the redactor.
- **Mutations from the real baseline.** Fusion reads the unchanged text of each changed file from a pristine candidate. It
  never mutates a file above the sharing bound, or one whose text does not hash to the change's precondition, and it says
  so.

### Configuration

The repository owner configures experiments in `fusion.config.json`, beside the confined checks. Configuring them has no
effect yet: tournaments are not wired into `fusion build` until the integration part of the delivery plan lands.

```json
{
  "verification": {
    "confinedCommands": [ { "id": "unit", "executable": "/usr/local/bin/node", "args": ["--test"], "cwd": ".",
      "timeoutMs": 120000, "mutationPolicy": "readOnly" } ],
    "experiments": {
      "probes": [
        { "id": "cli-help", "expect": "baseline",
          "command": { "executable": "/usr/local/bin/node", "args": ["bin/cli.js", "--help"], "cwd": ".", "timeoutMs": 30000, "mutationPolicy": "readOnly" } },
        { "id": "rounding", "expect": { "exitCode": 0, "stdout": "1.23\n" },
          "command": { "executable": "/usr/local/bin/node", "args": ["scripts/round.js", "1.225"], "cwd": ".", "timeoutMs": 30000, "mutationPolicy": "readOnly" } }
      ],
      "property": [
        { "id": "round-trip", "seedArg": "--seed", "casesArg": "--cases", "cases": 200,
          "command": { "executable": "/usr/local/bin/node", "args": ["test/properties.js"], "cwd": ".", "timeoutMs": 120000, "mutationPolicy": "readOnly" } }
      ],
      "mutation": { "maxPerCandidate": 2 }
    }
  }
}
```

Parsing is strict:
- Fusion derives each command's id (`probe-<id>`, `property-<id>`, `fuzz-<id>`), so an experiment cannot shadow a
  configured check.
- Every command must be a read-only command with an absolute executable inside the confined runtime.
- `seedArg` and `casesArg` must be plain flags.
- Mutations are opt-in.

## Selection (`src/core/tournament/selection.ts`)

No confidence score, no vote, no model preference.

1. **Elimination** by Fusion's evidence:
   - a security violation stops the whole tournament;
   - a failed proof obligation (BLOCKED);
   - a contradiction by one of Fusion's experiments;
   - an incomplete common profile;
   - a required falsification that did not end clean;
   - any decision other than VERIFIED.
2. **Convergence:** verified candidates that made the identical change are that one change.
3. **Dominance** over host-observed dimensions: fewer mutations the checks did not detect (compared only when every
   candidate had mutation runs), no new dependency, fewer changed files, fewer changed lines. A candidate dominates another
   when it is no worse on every dimension and better on at least one. A smaller patch never wins over stronger evidence by
   itself.
4. Several undominated verified candidates are a **tie**: `MULTIPLE_VERIFIED_CANDIDATES`, a human decision, shown with the
   host-observed differences, including where the compare probes show the candidates behaving differently. When a
   discriminating experiment (a compare probe, or a mutation run) did not complete for a tied candidate, the tie is
   `DISCRIMINATOR_INCONCLUSIVE` instead: Fusion could not look at everything it was asked to. A tied candidate you choose
   is still revalidated before any delivery. A choice outside the tie is no choice.

Outcomes are never collapsed into "failed":

| Outcome | When |
| --- | --- |
| `DELIVERY_ELIGIBLE` | One candidate was selected (by evidence or by your choice in a tie) and passed its fresh revalidation. |
| `NO_VERIFIED_CANDIDATE` | Candidates were judged and none is verified. |
| `MULTIPLE_VERIFIED_CANDIDATES` | A tie, and every discriminating experiment completed. |
| `DISCRIMINATOR_INCONCLUSIVE` | A tie, and a discriminating experiment did not complete. |
| `TOURNAMENT_BUDGET_EXHAUSTED` | Every candidate failed, and at least one because its deadline stopped it. |
| `CANDIDATE_SECURITY_VIOLATION` | A candidate's run, Fusion's re-materialization or a change of your checkout stopped the tournament. |
| `VERIFICATION_PROFILE_FAILED` | The common profile did not complete for any judged candidate. |
| `FALSIFICATION_REQUIRED_FAILED` | A required falsification did not end clean for any judged candidate. |
| `REVALIDATION_MISMATCH` | The selected candidate did not pass its one fresh revalidation; it is not retried. |
| `PROVIDER_FAILURE` | Every candidate's author failed to produce a change. |
| `CANDIDATE_MATERIALIZATION_FAILED` | Every candidate failed to materialize, or the selected one could not be materialized again. |
| `CANCELLED` | You cancelled the tournament. |

## Manifests (`src/core/tournament/manifest.ts`)

A candidate manifest binds:
- the task contract and base commit;
- the evidence snapshot;
- the frozen profile;
- the candidate's proposal and the tree state Fusion produced from it (the host application ledger);
- its changed paths and the policy version.

A corrected or mutated change is another revision with another manifest, so its evidence can never stand in for this one's.
The tournament manifest binds the candidates' manifests, the selection and the revalidation.

## The tournament run (`src/app/tournament/run.ts`)

1. **Frozen baseline.** Before any candidate exists, Fusion freezes the profile and records its SHA-256 with the
   contract and the evidence snapshot. It runs its checks on the unchanged baseline in a fresh pristine candidate, when the
   reliability policy asks for a reproduction, and records its probes' reference outputs.
2. **Independent candidates.** Each candidate is one run of the unchanged v0.4 engine:
   - its own run id, strategy brief, provider sessions, views and private candidate;
   - bounded parallelism (at most 2 at a time);
   - a candidate's security violation stops its siblings too.
3. **Evaluation.**
   - Each candidate that produced a change gets a manifest (its revision) and the v0.4 evidence decision.
   - Only candidates that decision already lets through spend budget on Fusion's experiments and mutations. Their
     decision is then taken again with the experiments as checks.
   - If a candidate's own baseline reproduction disagrees with the frozen profile, the baseline is not deterministic, and
     the profile does not hold for that candidate.
4. **Selection and revalidation.**
   - The primary checkout's fingerprint must be unchanged.
   - Selection follows the rules above.
   - The selected candidate is revalidated exactly once, in a fresh candidate with the identical tree.
   - Only then does the revalidated result go to the unchanged v0.4 delivery, bound by its proposal digest.

### Records: explicit binding, never event order

Candidates run concurrently, so their events interleave in the run's event log. Every tournament event carries an explicit
**scope**:
- the tournament id;
- the candidate id, when the event concerns one;
- the candidate's revision (its manifest SHA-256), once one exists.

The event store validates the scope strictly for each event type. The tournament's decision event binds:
- the outcome;
- the selected candidate and its revision;
- whether Fusion or a human chose it;
- the event id of the v0.4 evidence decision that permits the delivery.

That event id is the fresh revalidation's decision, scoped to exactly that candidate and revision.

The run summary (`fusion show`, `fusion history`) resolves a tournament only through this binding. The position of an event
in the log plays no part. If the binding does not hold, the tournament is shown as unresolved, with no evidence and no
guessed state. Examples:
- another candidate's decision;
- a candidate-stage decision;
- another revision;
- two decisions, or none;
- an "eligible" outcome bound to an undeliverable decision.

The same finding id in two candidates' reviews is two findings. A run without scopes is summarized exactly as in v0.4. A
v0.4 CLI refuses a log with scoped events rather than misreading it.

## In `fusion build`

- **The route is part of the plan you confirm.**
  - `fusion build` computes the route from the same host facts as its reliability plan: task class, security
    sensitivity, risk, competing explanations of a checked finding, and an earlier failed attempt. The last attempt counts
    when one of the last 10 builds of exactly this task text ended failed, timed out or with a decision required.
  - A tournament plan shows a `Candidates:` line with the count and the reason; a single-candidate plan reads exactly as
    in v0.4.
  - Your confirmation binds the count: a build confirmed for one candidate cannot start a tournament, and a single
    confirmation authorizes exactly what it did in v0.4.
- **Budgets you control.**
  - `--candidates 1|2|3` sets the number yourself.
  - `limits.maxCandidates` (1–3) in `fusion.config.json` is the repository owner's budget: it caps the policy's default,
    and a request above it is refused before any model turn.
  - With `limits.maxCandidates: 1`, every build takes the v0.4 route exactly.
- **Ties.**
  - At an interactive terminal (`fusion build` or the shell), a tie shows the tied candidates and Fusion's host-observed
    differences, then asks you to choose. Only an exact candidate id chooses; anything else chooses none.
  - With `--json`, or without a terminal, nothing is asked: the tie is the outcome.
  - A chosen candidate is revalidated freshly before any delivery.
- **Delivery.**
  - Only a `DELIVERY_ELIGIBLE` tournament reaches the unchanged v0.4 delivery, with the selected candidate's revalidated
    result.
  - That result's ChangeSet must be exactly the one the candidate's manifest binds, at the selected revision, with a
    deliverable decision. Anything else is refused as a security violation.
  - The delivery manifest lists Fusion's experiments among the verification checks (`x:<experiment>`).
  - An offline rehearsal is never delivered.
- **Outcomes**, as `fusion build` reports them:

| Tournament outcome | State | Exit |
| --- | --- | --- |
| `DELIVERY_ELIGIBLE` | `COMPLETED` (a delivery is prepared) | 0 |
| `MULTIPLE_VERIFIED_CANDIDATES`, `DISCRIMINATOR_INCONCLUSIVE`, `NO_VERIFIED_CANDIDATE`, `VERIFICATION_PROFILE_FAILED`, `FALSIFICATION_REQUIRED_FAILED`, `REVALIDATION_MISMATCH` | `DECISION_REQUIRED` (code = the outcome) | 13 |
| `TOURNAMENT_BUDGET_EXHAUSTED` | `TIMED_OUT` | 7 |
| `CANDIDATE_SECURITY_VIOLATION` | `FAILED` | 4 |
| `CANDIDATE_MATERIALIZATION_FAILED` | `FAILED` | 8 |
| `PROVIDER_FAILURE` | `FAILED` | 6 |
| `CANCELLED` | `CANCELLED` | 130 |

- **What you see.** The terminal shows, per candidate:
  - its strategy and state;
  - its v0.4 decision;
  - any contradictions and mutations detected;
  - why it failed or was rejected.

  Then the selection or tie with Fusion's reasons, the revalidation and the outcome. `fusion show` resolves a tournament
  through its binding (see above). No model reasoning and no score is shown.

## Offline routing calibration (`src/core/tournament/calibration.ts`, `scripts/v05-routing-calibration.mjs`)

The routing policy is versioned code, and it stays that way: nothing learns online and nothing rewrites the policy. What
v0.5 adds is the evidence to review a policy change against.

- **Recorded.** Every Writer build records its route decision (`RouteDecided`) before any model turn:
  - the policy version;
  - single or tournament;
  - the candidate count and who decided it (policy, you, or a model's advice within the policy's bounds);
  - the host facts it read: task class, sensitivity, risk, the number of competing explanations, an earlier failed attempt;
  - the repository's candidate budget.

  These are labels and counts only: no task text, no path, no model text.
- **Collected offline.** `node scripts/v05-routing-calibration.mjs [--repo <dir>] [--limit <runs>] [--policy <id>] [--json]`
  reads the last runs' own records in `.fusion/runs`. It is read-only, starts no provider and writes nothing. For each
  routed build it takes:
  - the outcome class;
  - for a tournament, its explicitly bound candidate evaluations (judged, verified, rejected, failed);
  - the selection class (only verified, converged, dominance, or your tie choice);
  - mutation counts.

  Runs without a route decision (read-only runs, or runs before v0.5) are skipped and counted.
- **What-if, honestly.** For each versioned candidate policy — the current `v0.5-route-1`, `single-always`,
  `fixes-at-any-risk`, `high-risk-only` — the report says, per task class and risk:
  - how many tournaments the policy would add or drop, and the change in candidate runs;
  - how many observed separations the dropped tournaments had, where a separation means Fusion's evidence rejected one
    candidate while it verified another;
  - for added tournaments, the expected separations: the group's observed rate times the count, and only for groups with
    at least 3 observed tournaments. Otherwise it says there is no estimate.

  Runs you routed yourself are kept as routed.

## Verification of v0.5 itself

Every invariant the program requires maps to its mechanism and the test that would fail on a plausible wrong
implementation: [v0.5 invariant matrix](v0.5-invariant-matrix.md). A test checks that every title the matrix quotes exists,
and that nothing is marked MISSING or PARTIAL.

The deterministic acceptance scenarios A–L run the product (`fusion build`) on a real Git repository, with the real
candidate port and the Docker backend over an in-memory daemon. The providers are scripted and told apart only by their
strategy briefs, so none of the scenarios depends on a real model making a mistake.
