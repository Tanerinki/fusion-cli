# v0.6 — sandbox network provisioning (maintainer gate)

**Status: released in v0.6.0, source checkout only** (the launcher is not in the packed CLI). This documents the
one-time administrator step that provisions the sandbox network boundary, and exactly what it changes. Everything Fusion
can do without elevation is already built and tested; this is the single elevated step, and Fusion never performs it
itself. The sandbox is not yet the provider execution path.

> **Limitation (I14, see [D12 in the matrix](v0.6-invariant-matrix.md)).** The loopback exemption this step adds is per
> package with no port granularity, and loopback traffic is not filtered by the firewall. The exempted sandbox can
> therefore reach **every** service on 127.0.0.1, not only Fusion's broker. Broker-only loopback is **NOT PROVEN**.
> Since the v0.6.0 release fix B1, `fusion sandbox doctor` reports this per identity: an exempted identity has deny-all
> network NOT enforced and a posture of at most CONFINED. Only an identity without an exemption is HARD for network.

## The network model (why a loopback exemption)

A Fusion sandbox runs an untrusted provider/candidate process in a Windows **AppContainer with no capabilities**, so it
has **no direct network access** — this is OS-enforced and mechanically proven by the `networkIsolation` canary
(for an identity without a loopback exemption, `fusion sandbox doctor` reports `network (deny-all): HARD`).

To let a provider reach **only** its API endpoint and nothing else, Fusion does not open the AppContainer to the
Internet. Classic Windows Firewall matches by IP/port, not by hostname, so it cannot by itself enforce "only
`api.<provider>`". Instead:

- the OS grants **one exception**, a **loopback exemption for the sandbox's AppContainer package SID**. With it the
  sandboxed process can reach the **host-side broker on `127.0.0.1`**, but no address other than loopback. It can also
  reach any other 127.0.0.1 service (see the limitation above);
- the **broker** (trusted, outside the sandbox) enforces the **FQDN allowlist** at the application layer.

So the operating system enforces *"only loopback is reachable"* (a package-SID-scoped boundary), not *"only the
broker"*, and the broker enforces *"which host"*. Fusion does **not** claim pure-OS FQDN enforcement; the split is
documented, not hidden. Until a broker is verified, the allowlist is never `ALLOWLIST_READY` (the posture model reports `NOT_PROVISIONED` or `BROKEN`), and any
execution that *requires* an allowlist fails closed with `NETWORK_POLICY_UNAVAILABLE` — never an unrestricted fallback.
`fusion sandbox doctor` itself requests no allowlist and does not verify a broker in v0.6.0, so it shows the allowlist
as not requested.

## What the provisioning does (and only this)

`fusion sandbox install` builds an **idempotent plan scoped only to Fusion's sandbox package SID**:

1. **Loopback exemption** for the package SID: `CheckNetIsolation LoopbackExempt -a -p=<SID>` — so the sandboxed
   provider can reach the host broker on loopback (and only loopback).
2. A **package-SID-scoped default-deny outbound firewall rule** in the named group `FusionSandbox`
   (`netsh advfirewall firewall add rule name="FusionSandbox deny egress" dir=out action=block package=<SID> ...`) —
   an explicit, auditable deny scoped to the sandbox (the AppContainer already has no network capability; this makes
   the deny explicit).

It is **idempotent** (keyed by the package SID and the named group), it **reports exactly what it changes**, it
**verifies** the resulting posture, and it **leaves every other application's networking and firewall policy untouched**
(the rules are package-SID-scoped, not machine-wide). `fusion sandbox uninstall` removes exactly this SID's exemption
and the named group — nothing else. A plan op that is not scoped to the sandbox SID/group is refused before anything is
applied.

## Why administrator is required

`CheckNetIsolation LoopbackExempt -a/-d` and `New-NetFirewallRule -Package` are **administrator-only** on Windows
(verified: unelevated they return access-denied). Reading the current exemption state (`-s`) is not, so
`fusion sandbox doctor` reports posture without elevation. Fusion **never elevates itself**; it presents the exact
command for you to run once from an elevated PowerShell.

## The one-time command

`fusion sandbox install --allow <host:port> [...]` (non-elevated) prints the exact command; run it **once** from an
**elevated PowerShell**. It is scoped only to Fusion's sandbox package SID; other applications are unaffected. After it
succeeds, `fusion sandbox doctor` for that identity reports:

- the loopback exemption as `present`;
- deny-all network as NOT enforced, and the overall posture as at most CONFINED;
- broker-only loopback as NOT PROVEN;
- the provider allowlist as not requested: doctor does not verify a broker in v0.6.0, so it never reports
  `ALLOWLIST_READY`.

`fusion sandbox uninstall` removes the exemption again.

Runtime execution after provisioning does **not** require administrator rights.
