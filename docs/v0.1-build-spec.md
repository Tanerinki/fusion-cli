# Fusion CLI V0.1 build specification

Status: implementation baseline, 2026-09-23. This specification is grounded in the local runtime capability report (`docs/research/local-runtime-capabilities.md`) and the external architecture and due-diligence PDF at the repository root. The later U4/U5 and structured-output results in the engineering brief supersede the older `[UNK]` entries in the runtime report. No provider inference is required for M0–M2.

## 1. Product boundary and invariants

Fusion is a standalone Node.js parent process. It owns policy, process lifecycle, workspaces, verification, event recording, and final status. Provider CLIs are direct child processes, never invoked through another provider's tool tree. Core role names are `Lead`, `Worker`, `Explorer`, `Reviewer`, and `Auditor`. Core workflow code must depend on capabilities and role bindings, never a concrete provider or model. Provider-specific flags, event schemas, auth checks, and model readback remain in adapters and transports.

The default policy may bind Lead to Claude Opus 5.5 and other roles to Muse Spark 1.3, but those values are configuration. A binding contains a provider ID, model profile, transport preference, and required capabilities. Changing a binding cannot require a workflow edit.

Success requires Fusion-owned deterministic verification. A model's claim that checks passed is evidence to investigate, never the verification result. A failed guard, unsupported capability, ambiguous auth lane, schema drift, unexpected write, or unavailable safe transport fails closed. There is no API-key fallback, automatic push/merge/rebase, destructive cleanup of the primary workspace, or automatic policy learning.

## 2. Runtime architecture and module ownership

```text
CLI → Task Inspector → Risk Gate → Policy Engine → Workflow Planner
                                       │                 │
                       Capability / Run / Billing State  DAG
                                                         │
                         Provider-neutral role runner → Provider adapters
                                                         │
                         WorkspaceLease + Context Packet + Artifact Store
                                                         │
                          Deterministic Verifier → Finding Engine
                                                         │
                                    Lead adjudication → Final result

Cross-cutting: EventStore, ProcessSupervisor, local metrics, cancellation.
```

| Module | Owns | Must not own |
|---|---|---|
| `core/domain` | Stable roles, task/context/result/finding/verification/event types; IDs; capability vocabulary | Provider names in workflow semantics |
| `core/policy` (M3+) | Eligibility, role binding, risk and billing decisions, retry bounds | Provider command construction |
| `core/workflow` (M9+) | DAG state transitions, fresh-session rules, adjudication | Direct process spawning or raw provider events |
| `platform/process` (M2) | Direct native spawn, argv, UTF-8 streams, JSONL framing, timeout, cancellation, tree cleanup, process metadata | Billing or provider protocol interpretation |
| `providers/*` (M4–M5) | Transport flags, protocol parsing, effective identity and auth assertions | Risk classification or verifier authority |
| `platform/workspace` (M7) | One writer lease per worktree, primary workspace protection, lease registry | Model prompts as a permission boundary |
| `platform/events` (M6) | Append-only run log and redacted artifacts | Credential values |
| `platform/verification` (M7) | Allowlisted commands and observed exit/diff results | Trusting agent-reported test outcomes |
| `cli` (M8+) | User-facing commands and exit codes | Provider-specific policy logic |

The M1/M2 package has no provider launch path. `ProcessSupervisor` is an internal primitive and is not wired to a CLI command until M3 guardrails exist.

## 3. Domain contracts

Types are in `src/core/domain.ts`; M1 is type-only. `AgentRole` is a closed union of the five roles. `ProviderId` and `ModelProfile.id` are opaque strings, so future providers require no core edit. `CapabilitySnapshot` records observed version/fingerprint and tri-state (`true`, `false`, `unknown`) capabilities for persistent sessions, structured output, filesystem read/write, shell availability/sandboxing, approval callback, protocol cancellation, usage reporting, model identity readback, and subscription lane readback. Unknown never satisfies a required capability.

`RoleBinding` connects role, provider, model profile, transport ID, and required capabilities. `AuthStatus` distinguishes authenticated (`subscription`, `subscriptionToken`, `api`, `thirdParty`) from unauthenticated/ambiguous (`unknown`) using a discriminated union; only provider adapters may populate it. `Session` carries opaque provider/transport identifiers, role, run ID, workspace lease ID, and posture. `TurnResult` requires output without error for completion, and an error for failure/cancellation. `VerificationResult` permits `passed:true` only with exit code zero. `DelegationPacket` transfers goal, constraints, acceptance criteria, file scope, decisions/invariants, required tests, and open questions. `ResultPacket` transfers status, changes, observed verification references, uncertainties, failures, and decisions requested. Full transcripts are not packet fields.

`Finding` is structured evidence: ID, severity, confidence, category, file/line span, claim, evidence, reproduction, realistic failure scenario, suggested fix, source provider/model/session/run, and adjudication. Verdicts are `CONFIRMED`, `PARTIAL`, `REJECTED`, `UNVERIFIABLE`. `VerificationPlan` contains only configured executable/argv/cwd entries; `VerificationResult` records timestamps, exit status, stdout/stderr artifacts, pre/post diff, and mutation flag. `RunEvent` is a discriminated, versioned envelope with run/step IDs, sequence, timestamp, kind, and redacted payload. `RunMetrics` aggregates task success, wall time, role assignments, agent runs/turns, context bytes, verification outcomes, findings/verdicts, rework/takeovers, intervention/retries, and usage. Subscription cost telemetry is named `estimatedListCostUsd`, never actual billed cost.

`ProviderAdapter` exposes capabilities, auth status, session create/resume, turn, cancel, usage, and close. A transport may report a capability unavailable and the policy must not silently substitute a weaker posture. Adapters return normalized errors while preserving redacted raw evidence references. M4 adds optional `webToolsDisabled` to the provider-neutral capability vocabulary. Unknown does not satisfy a reviewer binding that requires web tools to be disabled. `ProviderUsage.subscription` carries observed subscription quota windows separately from token counts and `estimatedListCostUsd`.

## 4. Process model (M2 contract)

`ProcessSupervisor.start` accepts an **absolute native executable path**, argv array, existing cwd, explicit environment, optional UTF-8 stdin, timeout, output byte ceilings, stream callbacks, and optional graceful cancellation hook. It always calls Node `spawn` with `shell:false` and `windowsHide:true`. It rejects `.cmd`, `.bat`, `.ps1`, and a bare command name. The provider adapter resolves a versioned native executable immediately before each run; the generic M2 resolver verifies the requested versioned `.exe` exists. User task text is never interpolated into a shell command. Prompt and schema files are written as UTF-8 without BOM by the later transport layer.

Stdout and stderr are independent, streamed with incremental UTF-8 decoders, bounded in memory, and returned separately. JSONL framing accepts `\n` and `\r\n`, buffers incomplete UTF-8 and lines, enforces a maximum line size, parses each complete JSON value once, and reports malformed input as a Fusion process/protocol error. A final unterminated line is parsed on EOF. Provider-specific event validation belongs to the adapter.

Cancellation is idempotent: record a Fusion-owned reason (`user`, `timeout`, `outputLimit`, `protocolError`, `shutdown`); invoke a transport's graceful/protocol hook; wait a bounded grace period; then terminate the process tree. On Windows, use `taskkill.exe /PID <numeric> /T /F` as the available baseline and fall back to the direct child kill if it fails. Record the chosen method and any failure independently of the child exit code. On POSIX, use a detached process group and kill its group. A Windows Job Object with `KILL_ON_JOB_CLOSE` is the preferred hardened backend where a reliable native binding is available; Node's built-ins do not expose Job Object assignment. M2 does not pretend the `taskkill` baseline provides Job Object guarantees. A later native backend can replace the tree terminator without changing transports. Keep the root child alive until tree termination to avoid PID/tree races. The remaining Job Object gap is tracked in §13.

`ProcessOutcome` includes executable/argv/cwd, PID if spawned, UTC start/end and duration, exit code/signal, separate captured streams with truncation flags, parser or spawn error, observer issues, initial stdin pipe-write status, and termination metadata. Pipe acceptance does not prove the child consumed the bytes. Observer exceptions do not become provider protocol errors or cancel a healthy child. Expected late stdin pipe errors do not mask the child's exit; explicit writes still reject to the caller. An abnormal exit does not become success because an agent printed success text. Timeouts and forced kills are visible as Fusion-owned state. The native resolver bounds version-file reads and validates the selected file immediately before spawn. Node cannot eliminate the stat-to-spawn race; a vanished binary is recorded as `SpawnFailure`.

## 5. Security and billing model (M3 onward)

Before every provider spawn, `BillingGuard` scans Windows environment keys case-insensitively. It refuses billing/API/gateway overrides, including `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, third-party Claude provider flags, `META_API_KEY`, Muse base URLs/custom routing, and relevant settings overrides. It strips provider parent-session variables and model/effort overrides, builds an explicit child environment, and never logs secret values. A subscription OAuth token may be forwarded only under an explicitly modeled subscription-token lane. A stored provider API key is not silently accepted. Post-spawn provider adapters assert effective auth lane, provider/model identity, and read-only posture from runtime readback. `account/read.state == accountLogin` is required for Muse subscription MSP. A model/catalog default is not sufficient evidence.

M3 implementation: `src/core/policy/billing-guard.ts` owns the provider-neutral ALLOW/STRIP/BLOCK scan, rejects duplicate Windows case spellings, strips unrelated credential variables, and returns a `SafeChildEnvironment` whose serialized form contains decisions but never values. Provider-specific rule sets live in `src/runtime/provider-environment-rules.ts`. Unknown provider-prefixed variables fail closed. `CLAUDE_CODE_OAUTH_TOKEN` is blocked by default; `strip` and `forwardExplicitSubscriptionToken` are explicit policy choices, and forwarding sets only a subscription-token *intent*, not proof of billing. The future adapter must prove the effective lane. `claudeSettingsBlockers` inspects parsed settings keys for `apiKeyHelper` and provider environment overrides without returning values; M5 must read the relevant settings file and supply blockers before launch. `DiagnosticRedactor` is a narrow utility for values, e-mail, organization IDs, and sensitive record keys; M6 EventStore must apply it at persistence boundaries.

`assertRuntimeEvidence` is the provider-neutral post-spawn gate. An adapter must report authenticated lane, effective provider/model, observed mechanical permission profile/posture, and a capability snapshot. Ambiguous auth, a mismatch, unobserved permission enforcement, or a missing required capability fails closed. Requested flags are never counted as observed evidence.

Reviewer posture is mechanical. Claude uses an explicit safe permission mode and a narrow read-only tool allowlist excluding shells, writes, network and inherited connectors; init readback must match. Muse read-only runs use `--disable-write --disable-shell --disable-web-tools --approval-judge off --no-foreign-personal-context`, then Fusion checks git status/content hashes. MSP host flags are process-wide, so different postures need different host processes. MSP approval decisions are normalized to `AllowOnce`, `AllowSession`, `Deny`, `Abort`, `Unknown`; `Deny` and `Abort` are negative. Deduplicate stages using session, approval, and current requirement identifiers. After a negative decision, allow a short grace period, then `turn/cancel`, optional interrupt, then supervised tree kill. Repository text and provider output are untrusted input to policy.

## 6. Transport gates (M4–M5)

Muse Exec: resolve the current versioned native binary immediately before a run, invoke `exec --json` with `--prompt-file`, explicit provider/model/effort and posture flags, parse JSONL incrementally, require `run.model.configured` effective identity, extract terminal output, validate final structured packet locally, and allow at most a bounded malformed-output retry. An explicit `maxModelSteps` maps to `--max-model-steps`; it is separate from the core `maxTurns` field. The Exec transport uses a separate guarded MSP `account/read` attestation before inference. Muse MSP: durable `muse serve` only, initialize/initialized, probe required methods and record schema fingerprint, start/read session, assert effective provider/model and `account/read`, route turn notifications, handle approval callbacks and cancellation, and fail closed when the required method set is absent. Exec may remain eligible for a workflow only if its own safety requirements are satisfied. The installed `muse serve` surface accepts only `--disable-write` and `--disable-shell` from the read-only flag set; `--disable-web-tools` is Exec-only, and MSP has no model-step cap field. Thus MSP reports `webToolsDisabled: unknown`, rejects an explicit model-step cap, and cannot satisfy a full read-only reviewer binding through `MuseAdapter` until a mechanical MSP web-tool control is proven. Its protocol transport remains testable directly with fake hosts.

Claude: one-shot native headless transport with explicit model, effort, safe permission mode, tool allowlist, stdin prompt, stream-json parsing, init assertions, nonzero/error classification and rate-limit handling. Undocumented persistent control protocol is outside V0.1. No provider code is implemented before M3 guards/tests.

M5 contract clarification: a Claude one-shot `Session` is a Fusion-local handle for one guarded turn at a time; it is not a durable Claude protocol session, so `persistentSessions=false`. Capabilities that require Claude init evidence remain `unknown` before a turn and are checked against the binding after init and before any result is trusted. The requested model alias and configured expected canonical model are separate; a mismatch in init fails closed. `estimatedListCostUsd` is list-price telemetry, not a subscription charge.

M5.1 settings preflight inspects exactly the workspace `.claude/settings.json`, workspace `.claude/settings.local.json`, profile `.claude/settings.json`, and any explicit caller-supplied settings object. A relevant file that is malformed, unreadable, oversized, or not a regular file blocks launch. Managed or enterprise settings outside these scopes are not claimed as pre-spawn-inspected. Claude init, tool, and auth assertions provide a second safety layer after spawn. A settings file can change between Fusion's read and the provider's spawn; this TOCTOU window cannot be eliminated by the current preflight.

M5.1 auth-status handling requires explicit logged-in and first-party evidence. A missing `apiKeySource` fails the ordinary subscription login lane. Claude Code 2.1.280 omits that field for an OAuth-token login; Fusion accepts this observed shape only when `CLAUDE_CODE_OAUTH_TOKEN` was explicitly forwarded through the guarded `subscriptionToken` lane and auth status reports `loggedIn:true`, `authMethod:oauth_token`, and `apiProvider:firstParty`. The headless init must still report `apiKeySource:none` before the turn can be trusted.

M5.2 init-only probe of native Claude Code 2.1.280, with `--restricted --safe-mode --tools Read,Grep,Glob --strict-mcp-config`, observed `agents` as four strings, `skills` as 18 strings, `slash_commands` as 53 strings, `capabilities` as five strings, and `plugins` as two objects with `name`, `path`, and `source`. No names, paths, prompts, or account values were retained. The same init reported `apiKeySource:none`, `permissionMode:dontAsk`, exactly `Glob,Grep,Read`, and no MCP servers. Anthropic's [headless documentation](https://code.claude.com/docs/en/headless#read-session-metadata) describes `capabilities` as protocol behaviors and `plugins` as successfully loaded plugins, so plugin count is effective load evidence rather than merely a discovered inventory. Its [CLI reference](https://code.claude.com/docs/en/cli-reference#cli-flags) says `--safe-mode` disables custom skills, agents, plugins, commands, and hooks, but managed policy hooks can still apply. `--tools` constrains built-in model tools; `--strict-mcp-config` and empty init MCP evidence constrain MCP. Agent/Skill/Task and plugin-provided executable tools are absent from the exact effective tool list. The headless CLI can expand user-invoked slash commands from a `-p` prompt, so Fusion also passes `--disable-slash-commands`. Inventory names are diagnostic, not proof of a callable tool. The two loaded plugin entries remain a security failure because their active contribution and origin were not established. Managed hooks remain unverified; absence of an init `hooks` field is not evidence of absence. Fusion requests hook lifecycle events and rejects any observed extension activity, while preserving this limitation. The inventory interpretation is version-gated to 2.1.280; an unvalidated version is ineligible even with the same flags.

M5.3 reconciles the installed 2.1.280 runtime. `claude plugin list --json` returned an empty installed inventory, while an init-only process still reported two successfully loaded built-in plugins. The local `--safe-mode` help explicitly says built-in plugins continue to work, clarifying the apparent discrepancy with the general CLI reference. A child-only `--settings` file containing dynamically derived `<name>@builtin: false` entries suppressed both; bare names did not. Fusion now performs BillingGuard and auth checks, reads the installed inventory, starts a strictly bounded init-only discovery process for built-ins, and cancels it immediately at init. Any startup hook/install event or unsupported source/version fails closed. It then writes UTF-8 temporary `enabledPlugins` settings, passes that path only to the reviewer child, and removes the file after the child exits. The final `system/init.plugins == []` assertion remains decisive for inventory/startup races and required plugins; exact tools, empty MCP, OAuth source, model identity, and hook activity are still checked. No user, project, managed, or global Claude settings or plugin state are modified by Fusion. The first full live turn exposed an informational `rate_limit_event`; Fusion now accepts only a validated event shape and rejects active overage billing. `--json-schema` was rejected because it added a fourth effective tool, so the final gate uses the exact three-tool set and a raw-JSON instruction with local packet validation. The final live gate passed on 2.1.280 with zero loaded plugins and a trusted terminal packet. Managed policy hooks remain explicitly unverified by absence of observed events. New Claude versions require a fresh live regression gate.

## 7. Workflow, workspace, and verification (M6–M9)

Risk Gate is deterministic and monotonic under new high-risk evidence. Low risk may run a single eligible role/tool plus verifier. Medium: Lead plan, one Writer in leased worktree, verifier, Lead review. High/critical: Lead architecture, optional read-only Explorer, one bounded Writer, verifier, fresh Reviewer, Lead adjudication, human gate for irreversible actions. Hard debug starts with one immutable evidence snapshot sent separately to Lead and Explorer; it compares hypotheses, reproduces, selects one Writer, runs regression verification, and uses fresh review. Audit uses a fresh Auditor with evidence findings and Lead validation. Architecture uses Lead proposal, independent challenger, and Lead final decision. Retry/review loops are bounded and recorded.

`WorkspaceLease` reserves at most one autonomous writer per Git worktree. Primary workspace remains untouched by autonomous writers. Dirty primary state is preserved; a worktree starts from a known commit or an explicitly chosen snapshot strategy. Lease registry enables crash recovery. No automatic stash/reset/clean/push/merge/rebase. Read-only reviews use host controls plus pre/post git and content-hash checks. `VerificationEngine` executes only configured executable/argv commands through `ProcessSupervisor`, records stdout/stderr and pre/post diffs, and flags verifier mutations. A check passes only when Fusion observed exit 0 and policy conditions hold.

## 8. Event, artifact, error, and metrics model

M6 uses `.fusion/runs/<run-id>/` with `run.json`, append-only `events.jsonl`, `artifacts/index.jsonl` and Fusion-owned artifact files, plus reserved `providers/`, `verification/`, and `findings/` directories. Optional `metrics.json` is written explicitly. `.fusion/` is gitignored. Events carry schema version, monotonic per-run sequence, timestamp, run ID, stable provider-neutral type, source, and a typed evidence payload. A truncated final JSONL line is diagnosed without rewriting prior events. Manifest and artifact files use temporary writes and rename; the artifact index remains append-only. See [M6 local run storage](m6-storage.md) for exact behavior and limitations.

Errors are typed by origin and policy consequence: `InvalidInput`, `CapabilityUnavailable`, `BillingBlocked`, `AuthMismatch`, `ProviderIdentityMismatch`, `SecurityViolation`, `SpawnFailure`, `Timeout`, `Cancelled`, `ProcessFailure`, `ProtocolError`, `MalformedOutput`, `VerificationFailure`, `WorkspaceConflict`, and `InternalError`. Include safe message, retryability, run/step IDs, and artifact references. Never use an exit code alone to infer cancellation or billing lane. Metrics are derived from events, stored locally, and never change policy automatically.

## 9. Testing and live-test contract

Default `npm test`, typecheck, lint (if configured), and build are deterministic and use only fake local executables/fixtures. They must not discover or invoke provider binaries. M1 tests check domain invariants through compilation and pure validation helpers where needed. M2 tests exercise partial UTF-8/JSONL chunks, CRLF/final line, malformed/oversize records, separate stdout/stderr, spawn failure, timeout, idempotent cancellation, graceful hook ordering, output caps, native resolver rejection, and Windows child-tree cleanup. Tests use local Node fixture children and process markers, never a provider CLI.

Real-provider tests require `FUSION_LIVE_TESTS=1` plus explicit `npm run test:live`. They are excluded from ordinary scripts and were not run during M4. The harness covers account login, effective model/provider, Exec structured output and read-only flags, MSP U4 veto and U5 cancellation; live results must be interpreted against the installed host behavior. Avoid mutating global provider auth/config. A failed live security assertion disables that transport capability until investigated.

## 11. Evidence reconciliation

The PDF's older recommendation to prioritize MSP and later metrics is refined by local runtime evidence and the engineering brief: Exec is a simpler first Muse transport, MSP is now live-proven for approval and cancellation but must be capability-gated, and metric event types are present from V0.1. The PDF's provider-specific role descriptions are default *bindings*, not core role names. The runtime report's `[UNK]` for U4/U5 and structured output is superseded by the brief's live PASS results. Its Muse shell sandbox uncertainty remains a real future Worker eligibility question; V0.1 must not grant a writer role based on an unproven sandbox.

## 12. Implementation order within this run

1. M0 specification and evidence reconciliation.
2. M1 strict TypeScript package, domain contracts, deterministic checks; inspect diff/status.
3. M2 process primitives, local fixtures and tests; run typecheck/tests/build; inspect diff/status.
4. Stop and report remaining architectural risks. No provider calls or auth changes.

## 13. Open implementation risks

- Windows Node.js does not expose Job Objects directly. M2 uses direct native children and `taskkill /T /F`; a native Job Object backend is required before claiming kill-on-parent-crash guarantees for arbitrary descendant trees. M7 observed that libuv places each Node process's non-detached children in its own kill-on-close job, but that job permits silent breakaway and is an implementation detail, so detached descendants remain uncovered (see [M7 hardening](m7-hardening.md)).
- Restricted Windows accounts may receive Access denied from `taskkill /T /F`; fallback metadata reports direct-child kill only and never claims descendant cleanup.
- The report found Muse's managed shell sandbox unavailable in several contexts. A future write-capable Muse Worker must remain ineligible until host isolation and live tests prove the boundary, or another safe writer mechanism is adopted.
- Provider CLI upgrades can change permissions, event schemas and MSP method availability. M4/M5 must probe and fail closed per version/fingerprint.
- Stored Muse auth semantics and Claude OAuth-token versus gateway-token ambiguity require M3 preflight rules and explicit lane representation; neither can be inferred solely from a generic auth-status field.
- Claude subscription-token forwarding remains an explicit configuration decision. M3 defaults to blocking an inherited token; M5 must connect the selected policy and runtime assertion. M3 provides a settings object scanner, while M5 must locate/read the effective settings files and use its blockers before any provider spawn.
