# v0.6 — Gate #2: real-provider HARD validation (§73)

**Status: NOT run. NOT released.** This is the second and final maintainer gate of v0.6. It is the first time a **real
provider process** is executed **inside** the Windows AppContainer HARD sandbox, end to end. Fusion never runs this gate
itself: it needs real provider credentials, consumes provider quota, makes a real outbound model call, and depends on the
Gate #1 network policy being applied. It is presented here as a plan + a single command; a human authorizes and runs it.

## Why this is a gate (and not a CI test)

Everything that can be proven *without* a real model has been proven:

- **Deterministic substrate (CI):** capability manifest, minimized environment, fail-closed posture, the run-spec
  document, durable journal/lease/checkpoints/replay/recovery, recoverable apply, candidate-result reuse (I7), exact
  human-gate resume (I8). See `v0.6-invariant-matrix.md` sections A2–A6, D6, D7.
- **OS enforcement (maintainer-run live, first pass 2026-09-29, Windows 11 Pro 26200, unelevated):** the native launcher
  creates a no-capability AppContainer with explicit DACL grants inside a kill-on-close Job; every confinement fact is
  proven under real OS denial, including that a sandboxed provider-like child is denied the primary checkout, sibling
  candidates, Fusion's journal/delivery and host credentials, and has no network capability (DENY_ALL). See section B and
  D4.
- **Network boundary (Gate #1, applied & verified by the maintainer):** `fusion sandbox doctor` reports overall posture
  HARD, `network (deny-all): HARD`, loopback exemption + broker present, scoped only to Fusion's sandbox package SID.

What remains can only be established by running a **real** provider inside HARD:

1. a real provider binary launches and runs to completion **under the AppContainer token** (posture stays HARD, never
   silently downgraded to unsandboxed);
2. from inside the sandbox the provider reaches **only** its allow-listed endpoint through the loopback broker, and
   nothing else (DENY_ALL + ALLOWLIST holds for a real network client, not just a canary);
3. the provider still produces a **valid ChangeSet** that Fusion host-validates against the writer scope — i.e. HARD
   isolation does not break the real production Writer path;
4. throughout, the provider is denied the trusted control plane (primary/sibling/journal/delivery/credentials), proven
   against a **real** provider process rather than a canary.

A fake adapter is never accepted as evidence for any of these. This is the gate.

## Integration status (audit, 2026-09-30)

- **DONE — `ProcessSupervisor` → AppContainer launcher (PR #59, I10).** When a `ProcessSpec` carries a `sandbox`,
  `ProcessSupervisor.start` spawns the native launcher (which runs the target inside a no-capability AppContainer, applies
  the manifest grants and minimized env, bridges stdio and exits with the child's exit code) instead of the target
  directly. Fail-closed is structural (`SANDBOX_UNAVAILABLE`, never unsandboxed). **Deterministic proof: PASS**
  (`test/v06-i10-supervisor-sandbox.test.ts`, 8 tests, CI). **Maintainer real-OS fake-provider proof: PASS**
  (`test/live/supervisor-sandbox.live.test.ts` — the real launcher OS-confined a provider-like child run through the
  production `ProcessSupervisor` branch). The supervisor wiring is no longer pending.

- **DONE — provider transport → HARD sandbox (PR #62, I11).** A `SandboxingSupervisor` wraps the Claude/Muse transport
  supervisor and attaches a `SandboxLaunch` to EVERY provider execution (auth readback, plugin/runtime discovery,
  attestation, quarantine, the turn); no `claude.exe`/muse binary runs on the host. Fail-closed is structural. HARD Claude
  requires the `subscriptionToken` lane (host-login is denied in the sandbox → fails closed); Muse has no token lane, so a
  HARD Muse turn fails closed at auth. **Deterministic proof: PASS** (`test/v06-i11-transport-hard.test.ts`, 7 tests, CI).

- **DONE — host-side provider network broker (PR #61, I12).** `src/platform/network/provider-broker.ts` is a real
  loopback-only CONNECT proxy: per-run credential, host-owned allowlist bound to the capability manifest, byte/connection/
  TTL budgets, sanitized logs, no open-proxy surface, no orphan. **Deterministic proof: PASS**
  (`test/v06-i12-provider-broker.test.ts`, 10 tests, CI). **Loopback boundary is NOT PROVEN**: `LoopbackExempt` is
  per-package, not per-port, so the exemption does not stop the sandbox from reaching unrelated localhost services directly
  (matrix D9). `UNRELATED_LOCALHOST_ACCESS = ACCESSIBLE` until WFP package-SID+port scoping is added or the residual is
  explicitly accepted.

- **NOT DONE — control-plane assembly of the HARD run.** Nothing in the control plane or provider adapters yet BUILDS a
  `hardProfile` or STARTS the broker for a real `fusion build`. The transports *accept* HARD and the broker *exists*, but
  no orchestration locates the launcher, starts a per-run broker, assembles the view/scratch/canary grants + the broker
  proxy env + the endpoint allowlist, applies the per-run loopback exemption (Gate #1, admin, for the ephemeral package
  SID), and passes the profile to the transport config. So `fusion build` still runs the provider unsandboxed by default.

- **NOT DONE — combined real-OS proof + real-auth viability.** The combined end-to-end proof (real transport → supervisor
  → AppContainer → authenticated broker → fake upstream) has not been run — it needs the control-plane assembly above, a
  per-run loopback exemption, and the real launcher. Whether `claude.exe` even runs with a synthetic writable HOME + the
  injected token + no host config is UNKNOWN until a real turn (Gate #2 itself).

**Consequence.** The two mechanisms (I11, I12) are built and deterministically proven, but the end-to-end path in the
header is **still not runnable** because the control-plane assembly + per-run loopback exemption are not wired and the
loopback boundary is unproven. A single `fusion build` command cannot exercise Gate #2 today: it would run the provider
unsandboxed (a HARD downgrade this program forbids). These must land — each behind deterministic + fake-provider(-live)
proofs, no real model call — before the one
authorized real-provider run below is meaningful.

## Preconditions (the maintainer confirms before running)

- Gate #1 applied and green: `fusion sandbox doctor` shows overall posture **HARD**, `network (deny-all): HARD`,
  loopback/broker present, scoped to the sandbox SID.
- A real Worker binding is configured (provider family, executable, runtime version) and authenticated; provider quota is
  available and the maintainer accepts spending it.
- A throw-away fixture repository (never a real project): a single-file, low-risk task, Worker-only flow.
- The run is understood to make a real outbound model call and to change no other machine state.

## Acceptance criteria (what the run must show, recorded as evidence)

The run passes only if **all** hold, each recorded (labels/hashes/counts only, never provider text):

1. **posture = HARD, not downgraded** — the provider ran under the AppContainer token; a `SANDBOX_UNAVAILABLE` fail-closed
   is a *fail*, never a silent unsandboxed fallback.
2. **filesystem confinement** — the real provider process (and any child) was denied the primary checkout, sibling
   candidates, `.fusion` journal/evidence/delivery and host credentials; only its Fusion-owned view (read) and scratch
   (write) were reachable.
3. **network** — DENY_ALL held; the provider reached only its allow-listed endpoint via the loopback broker; a control
   attempt to any other host was refused.
4. **environment** — the child received only the minimized, allow-listed environment; no credential-shaped host var
   leaked in.
5. **production Writer path intact** — the provider produced a ChangeSet that Fusion validated against the writer scope
   and host-applied into the private candidate, verified in the accepted confined backend (as in the pre-v0.6 real-provider
   probes), now additionally under HARD isolation.
6. **no contamination** — no injected credential sentinel appeared in the provider's output, the recorded artifacts/logs
   or any prepared delivery.

Any failure leaves v0.6 unreleased; the gap is recorded honestly, never downgraded to a limitation to finish.

## The single command — still blocked (control-plane assembly + loopback exemption + combined proof)

There is intentionally **no runnable single command yet**. The two mechanisms (I11 transport→HARD, I12 broker) are merged
and deterministically proven, but a real `fusion build` still runs the provider unsandboxed because nothing assembles the
HARD run (locate launcher → start per-run broker → build the view/scratch/canary grants + broker proxy env + endpoint
allowlist → apply the per-run loopback exemption → pass the profile to the transport). Presenting a command now would run
the provider unsandboxed (a forbidden HARD downgrade). The command this gate will use, once the assembly lands and the
combined real-OS proof passes, has the shape:

```powershell
# 1. confirm the network gate is live (available today)
fusion sandbox doctor

# 2. the authorized real-provider HARD validation run — NOT runnable until the control-plane assembly + per-run
#    loopback exemption land and the combined real-OS proof passes; Claude only (Muse has no token lane)
$env:FUSION_SANDBOX_POSTURE = 'hard'; fusion build --path src/<one-file> "<the fixture's single-file task>"
```

Because release-critical boundaries are unproven (loopback boundary; combined real-OS proof; real-auth viability) and the
assembly is unwired, **READY_FOR_GATE_2 = NO**.

The exact posture flag/env and the broker's `HTTPS_PROXY` wiring are finalized with those integrations. The verified
binding is **Claude, subscription auth** (executable `claude.exe`; lane `subscription` or `subscriptionToken` via
`CLAUDE_CODE_OAUTH_TOKEN`; third-party keys and `ANTHROPIC_BASE_URL` are blocked), so no API key is entered and the broker
must be a CONNECT proxy, not a base-URL swap.
