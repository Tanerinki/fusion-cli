# v0.3 — validating Muse Exec 1.4.0-R4302.1 for the Reviewer binding

Labels: **STAGE 1 PREPARED** (offline, mechanically enforced), **LIVE: NOT RUN**, **NOT VALIDATED**.

## Why

On 2026-09-27 (21:45 UTC) Muse updated itself on the maintainer's machine.

- **The swap.** `muse-bin-1.4.0-R4302.1.exe` replaced `muse-bin-1.4.0-R4161.1.exe`, and `.muse-version` now selects
  1.4.0-R4302.1.
- **Why the Reviewer is refused.** Fusion's Reviewer validation (O5.5B24) is bound to the release 1.4.0-R4161.1 **and**
  its binary's SHA-256. Fusion therefore correctly refuses the new binary: the Reviewer's read-only posture reads
  `unknown`, and no investigation or review runs on it.
- **The consequence.** The v0.3 live acceptance stops at its precondition, before any model turn.

Nothing is downgraded and no 1.4.x range is admitted. This milestone validates the one installed binary, or not.

## The one live turn (maintainer, normal PowerShell window)

The probe refuses to start inside an AI coding tool: there, Muse model calls lose network access. Run it once, from a
normal PowerShell window, with Docker Desktop running (the candidate is verified in the confined backend):

```powershell
cd "D:\apps backup\fusion-cli"
git switch main
git -c http.sslBackend=schannel pull --ff-only
npm ci
npm run build
node dist/test/live/reviewer-probe.js --authorization V0.3-MUSE-R4302-REVIEWER
```

It prints about ten lines: the outcome, stage, process counts, candidate verification, the account readback, the review
contract and model, and the terminal and reply-envelope labels. It holds no model text. Send those lines back. The
evidence file stays in `%TEMP%\fusion-v03-muse-r4302-reviewer\`. **Do not run it twice**: the authorization is one-shot.

## Stage 2 (after the run)

1. **Independent review of the evidence file.** No provider is called and nothing is re-run. The checks are O5.5B24's:
   - namespace and claim;
   - harness identity;
   - the authorization, grant and pins;
   - the binary before and after;
   - the account readback, before and after, `authenticated`/`subscription`;
   - the processes (exactly the pinned binary, only the production controls);
   - the review (contract accepted, `observedModel` `muse-spark-1.3`, raw-only envelope);
   - integrity and cleanup;
   - redaction.
2. **Only on a PASS** that survives that review is 1.4.0-R4302.1 recorded as a `BindingValidation` next to R4161.1's. It
   covers exactly this Reviewer binding and this SHA-256, and the authorization becomes `consumed`. The regression matrix
   then proves eligibility for exactly that binding and binary, and refusal for everything else. The Explorer binding
   stays unvalidated.
3. **Any other outcome** records the failure, and the Reviewer stays refused.
