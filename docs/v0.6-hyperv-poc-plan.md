# v0.6 — Hyper-V isolated-worker PoC plan (Option C, bounded, maintainer-run)

**Status: PLAN + mechanical test matrix + RESULT template. NOT run. Fusion is NOT committed to this backend.**

This is the bounded proof-of-concept for **Option C** (network-namespace-isolated provider worker) from
`v0.6-network-isolation-spike.md`. Its sole purpose: determine **mechanically** whether a Hyper-V isolated Windows worker
can satisfy **every** existing v0.6 HARD invariant with a smaller trusted computing base than a custom kernel driver.

## Why this is maintainer-run (not run here)

Creating a Hyper-V isolated Windows container, configuring an HNS network with VFP ACLs, and running real socket / filesystem
/ process canaries **inside** it requires a real Windows host with **administrator** rights and the Hyper-V + Containers
features — the same real-OS boundary as the live AppContainer proofs (which the maintainer ran, 2026-09-29). This session
cannot execute Hyper-V/HCS/HNS/VFP or the mechanical canaries, and this program forbids inferring the boundary from rule
presence. Therefore **every RESULT field below is `NEEDS_PROOF` until the maintainer runs the harness**; the "Expected"
column is analysis from documented Windows behavior, explicitly NOT a measurement.

## Target architecture (do NOT reproduce broad LoopbackExempt)

```
Fusion trusted host (control plane + broker)
   → dedicated host-side egress broker endpoint (a specific host/vSwitch IP:port, NOT host loopback)
   → HNS/VFP-enforced worker vNIC policy  (ALLOW worker → broker IP:port ONLY; DENY all else)
   → Hyper-V isolated Windows worker (own network namespace)
   → untrusted provider process
```

The worker reaches ONLY the dedicated broker endpoint (network-enforced); the broker then enforces the FQDN/port allowlist
(I12) with the per-run credential as **defence in depth, not the network boundary**.

## 1. Network-mode investigation (mechanical)

Microsoft docs indicate default **NAT/Transparent** networks for Hyper-V-isolated containers cannot have their port ACLs
reconfigured, while **L2Bridge / L2Tunnel / Overlay** carry policy via **VFP**. Verify on the host; choose the smallest HNS
mode that supports an ACL equivalent to: ALLOW `worker → brokerIP:brokerPort`; DENY worker → {every other host addr/port,
LAN, Internet, host loopback, other container/VM endpoints}. Prove with real sockets, not rule presence.

## 2–12. Mechanical test matrix (the harness runs all of these; disposable canaries only, no real provider)

**Network canary (from inside the worker, fake provider attempts real sockets, incl. direct sockets ignoring proxy env):**

| # | Attempt | Expected |
| - | --- | --- |
| A | dedicated Fusion broker endpoint | ALLOWED |
| B | another port on the broker host IP | DENIED |
| C | host `127.0.0.1` arbitrary listener | DENIED |
| D | unrelated host service | DENIED |
| E | LAN canary listener | DENIED |
| F | arbitrary Internet IP | DENIED |
| G | arbitrary DNS / unrelated destination | DENIED unless the controlled broker arch requires it |
| H | direct provider endpoint bypassing broker | DENIED |

**Filesystem HARD boundary (real reads/writes, disposable secret canaries, not mount metadata):** VIEW read ✓ / VIEW write
✗; SCRATCH write ✓; DENIED = primary checkout, sibling candidate, Fusion journal, Delivery store, recovery vault, host user
profile, SSH/browser/credential locations, unrelated projects. The provider must NOT see the host filesystem just by being
in the worker.

**Process-tree containment:** fake provider spawns child → grandchild; cancel/terminate the worker run; prove root+child+
grandchild gone, worker disposed, no surviving process, no orphan VM/container. Compare to the kill-on-close Job invariant;
if the worker lifecycle is stronger, record that honestly.

**Ephemeral worker:** after termination prove no provider-created persistent state, no stale credentials, no writable
candidate state outside intended persistence, no stale networking ACL, no stale mounted share, no stale worker process. A
new run inherits no arbitrary state.

**Broker architecture:** broker stays trusted host infra, bound to the dedicated worker-network endpoint (NOT broad
loopback); worker authority = worker network endpoint + exact broker IP + exact broker port + per-run credential +
manifest/policy hash + lifetime; the **network layer enforces reachability independently of the credential**.

**DNS:** prefer the untrusted worker needs NO arbitrary DNS (all egress via the broker) → deny it; if required, define an
explicit trusted DNS path proven not to become an egress/bypass channel. No default DNS for convenience.

**Provider compatibility (inspection only, fake binary first):** whether the native Windows provider executable shape can
run in the worker — runtime deps, working dir, HOME/USERPROFILE behaviour, explicit OAuth-token env, certificate trust
store, HTTPS_PROXY support. Do NOT grant the host user profile into the worker.

**Hyper-V security properties:** enumerate exactly what Hyper-V isolation / HCS / HNS / VFP / container FS / host mounts /
worker lifecycle each provide. "Container" alone is not HARD; every Fusion HARD invariant still needs its own mechanical
proof.

**Performance (informational, do not optimize):** cold/warm start, memory overhead, base image size, worker create/destroy,
candidate-view materialization cost.

**Dependency audit:** Hyper-V feature, Containers feature, HCS/HNS APIs, container runtime (if any), base image, admin
provisioning, image servicing. Prefer Windows-native HCS/HNS for the long-term architecture. Do NOT make Docker Desktop an
architectural trust dependency; using a runtime temporarily to establish feasibility is acceptable ONLY if the evidence is
explicitly labelled PoC.

## 14. Stop conditions (built into the harness)

contain the complete process tree → **STOP, do not weaken HARD.** If it succeeds clearly → continue only through a focused
architecture proposal for the production Hyper-V backend. No real provider call; no v0.6 release; no v0.7.
