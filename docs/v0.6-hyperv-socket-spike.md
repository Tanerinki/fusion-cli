# v0.6 - no-NIC host/guest transport spike (Hyper-V socket / VMBus)

**Status: FEASIBILITY SPIKE (research only). No implementation, no elevated mutation, no real provider, no live run.
`BROKER_ONLY_NETWORK_BOUNDARY = NOT_PROVEN`, `READY_FOR_GATE_2 = NO`.**

Goal: a provider worker with **no NIC / no IP path** off its own loopback, whose only egress is a non-IP host/guest
channel to the trusted Fusion broker. This removes the dependency on VFP ACLs (rejected: `internal`/ICS doesn't enforce
them - `v0.6-hyperv-network-diagnosis.md`) **and** on physical-NIC / external-vSwitch changes (l2bridge - which we
refuse to make a product requirement).

## PHASE 1 - feasibility (primary sources + one observed fact)

### What Hyper-V sockets are
Hyper-V sockets (`AF_HYPERV`, `SOCK_STREAM`, `HV_PROTOCOL_RAW`; Linux guests `AF_VSOCK`) are host<->guest datagram/stream
channels that run **"without using networking ... all data stays on the same physical memory"**
([Make your own integration services](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/make-integration-service)).
- Addressing is non-IP: `SOCKADDR_HV{Family, Reserved, VmId, ServiceId}` - a **VM GUID** + a **service GUID**; no IP/DNS.
- A host **service** is registered under `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Virtualization\
  GuestCommunicationServices\<ServiceGUID>` (`ElementName`). **Registration requires administrator** and is a
  **one-time** host change (fits a `fusion sandbox install`, not a per-run mutation).
- Container-relevant addressing exists: `HV_GUID_PARENT` (`a42e7cda-...`) - *"The parent of a container is the
  container's host ... Listening on this VmId accepts connection from (Inside containers): Container host."* So the
  HvSocket address model is **container-aware** at the OS level.

### The A / B / C classification (B is NOT inferred from A)

| transport | A: normal Hyper-V VM | B: Hyper-V-ISOLATED Windows container payload | evidence |
| --- | --- | --- | --- |
| **Raw `AF_HYPERV` from a user app, host service via GuestCommunicationServices** | **SUPPORTED** (documented) | **NOT ESTABLISHED (treat as C)** - Docker does not expose arbitrary HvSocket service registration or `AF_HYPERV` to container payloads; no MS doc states a container-*guest user app* may open `AF_HYPERV` to a custom host service. HvSocket *is* used inside HCS for its own GCS control channel, but that is HCS's channel, not an exposed app transport. | docs (A); no doc/observation for B |
| **Mapped named pipe over VMBus (`--mount type=npipe`), worker `--network none`** | n/a (pipe mounts are a container feature) | **SUPPORTED + OBSERVED on this host** - Docker exposes `--mount type=npipe`; for Hyper-V isolation HCS proxies the host named pipe to the guest over the **VMBus pipe** (an HvSocket-family, non-IP transport). | Docker docs + **session-1 observation** (below) |

**Observed fact (session 1, this host, not inferred):** a Hyper-V-isolated worker started with `--network none` plus
`--mount type=npipe,source=\\.\pipe\<run>,target=\\.\pipe\<run>` round-tripped bytes to a **.NET** `NamedPipeServerStream`
on the host (a node/libuv *client* in the guest worked; a node/libuv *server* on the host did **not** - so the host side
must be a .NET/Win32 pipe server). Critically, the guest could enumerate only the **one mapped pipe** plus its own
container-internal pipes - it could **not** see arbitrary host pipes. With `--network none` the guest had loopback only.

### Conclusion of Phase 1
- The **raw `AF_HYPERV`** path from the container payload is **C** (not a supported/ exposed container-app transport) - do
  not build on it.
- The **mapped named pipe over VMBus** is the **supported HCS-exposed, no-NIC equivalent** the mission's diagram hedged
  on ("AF_HYPERV **or the actual supported HCS equivalent**"), and it is **B: observed working here**. It gives exactly
  the intended property: the only non-loopback egress is one explicitly-mapped non-IP channel.

## PHASE 2 - product fit (minimum architecture, if built later)

```
Hyper-V-isolated worker  (docker run --isolation=hyperv --network none)   <- NO NIC, NO IP, loopback-only
  provider  (HTTPS_PROXY=http://127.0.0.1:<guestPort>)
     v
  Fusion guest shim  (tiny Fusion process, listens 127.0.0.1:<guestPort>, speaks HTTP CONNECT)
     v   (writes tunnel bytes to the mapped pipe)
  mapped named pipe  \\.\pipe\FusionV06-<runId>   (HCS -> VMBus pipe; non-IP)
     v
  Fusion host broker  (.NET/Win32 NamedPipeServerStream; per-run credential; destination allowlist; egress)
     v
  approved provider API
```

- **Worker network:** `--network none` - no endpoint, no NIC, no IP. (Simpler and stronger than any ACL: there is no IP
  path to allow or deny.)
- **Guest shim:** Fusion-owned; the provider's only proxy is `127.0.0.1:<guestPort>` on the worker's own loopback.
- **Host broker:** a .NET/Win32 named-pipe server (node/libuv server did not work over the VMBus pipe); it authenticates
  the per-run credential, enforces the exact destination allowlist, performs egress. Reuses the existing provider-broker
  allowlist/credential logic conceptually (transport swapped from TCP-CONNECT to pipe-framed CONNECT).
- **Service/pipe lifecycle:** an **ephemeral per-run random pipe name** (`FusionV06-<runId>`); created at run start,
  closed at teardown. No GuestCommunicationServices GUID needed for the pipe path (that is only for raw `AF_HYPERV`).
- **Auth guest<->host:** per-run unguessable credential presented in-stream (as today), over a pipe that (a) the guest
  cannot enumerate and (b) only the mapped-in instance is reachable from the guest; host pipe DACL scoped to the minimal
  principal the HCS proxy connects as, else Everyone + credential + ephemerality as defence in depth (to be pinned down
  in the PoC).
- **Provider credentials:** the worker receives only the synthetic per-run broker credential (unchanged).
- **FS / process / cleanup:** unchanged from the current harness - view(ro)/scratch(rw) mounts, no broad host mount, no
  Docker/HCS pipe exposed, kill-on-close process tree, deterministic prefix-scoped cleanup.
- **Admin model:** the named-pipe path needs **no** admin and **no** host network/registry change (session 1 ran
  non-elevated; `docker run --mount type=npipe` is a docker-users operation). A one-time `fusion sandbox install` remains
  acceptable for the AppContainer/FS HARD side, but the **transport** itself requires neither per-run nor install-time
  network mutation. **No** NIC/WLAN/Ethernet/external-switch/route/firewall/DNS/Docker-network change - meeting the
  product requirement.

## PHASE 3 - security canaries (PoC design, not run)

ALLOW (one path only): provider -> guest loopback shim -> mapped pipe/VMBus -> host broker -> synthetic provider, with a
token round trip.
DENY (all by construction of `--network none`, proven adversarially, not assumed):
- worker -> host localhost / host LAN IP / LAN / Internet / direct synthetic provider: **no NIC, so no route** - raw
  sockets (ignoring `HTTPS_PROXY`) have nowhere to go; each attempted with a host positive control (host reaches it,
  worker cannot) so a timeout is a proven deny, never INCOMPLETE-by-accident.
- raw socket bypassing the proxy: same - structural deny (no adapter).
- unauthorized destination through the broker: broker returns refused.
Plus the existing matrix: no broad host mount; no Docker/HCS control pipe exposed to the provider (only the one Fusion
pipe is mapped; the guest cannot enumerate others); view read-only; scratch writable; primary/sibling/control-plane/
host-profile inaccessible; process tree dies with the worker; cleanup complete.

Note: `--network none` makes the hardest canaries (LAN/Internet/host-port) **structural** denials rather than
policy-enforced ones - a stronger result than the VFP-ACL design was attempting, and it sidesteps the
host-directed-bypass that killed the `internal` design.

## PHASE 4 - decision

**HYPERV_SOCKET_WORKER = FEASIBLE_FOR_POC** - via the **mapped named pipe over VMBus** (`--mount type=npipe` +
`--network none`), the supported HCS-exposed no-IP host/guest transport (B: observed on this host). The **raw
`AF_HYPERV`-from-container-payload** variant is **C** (not an exposed/supported container-app path) and is NOT the basis
of the PoC.

### Smallest isolated PoC plan (design only; implement later, on request)
1. Build the worker image (existing `build-worker-image.ps1`); run it `--isolation=hyperv --network none` with one
   `--mount type=npipe` of an ephemeral `\\.\pipe\FusionV06-<runId>`. No other mount; no NIC.
2. Host broker = a small .NET/Win32 named-pipe server (NOT node/libuv as the server) that frames CONNECT, checks the
   per-run credential + destination allowlist, and bridges to a synthetic provider listener. Reuse the provider-broker
   allowlist/credential semantics.
3. Guest shim = a tiny Fusion process on `127.0.0.1:<guestPort>` that accepts the provider's CONNECT and relays bytes to
   the mapped pipe (node *client* to the pipe is proven to work).
4. Run the ALLOW path (token round trip) + the DENY canaries above, each with a host positive control; reuse the
   existing evaluator/verdict machinery unchanged (no weakening).
5. Pin the host pipe DACL to the minimal principal; keep the per-run credential + ephemeral pipe regardless.
6. STOP and report; no integration before a clean mechanical PASS. No real provider.

This reclassifies the named-pipe option that the first iteration set aside: it is now the **leading** candidate because
TCP+VFP is rejected, l2bridge needs refused NIC changes, and `--network none` + one mapped pipe is a **stronger**,
no-host-network-mutation security story. The earlier concerns are addressed: host server is .NET/Win32 (proven); the
"Everyone" DACL is replaced/augmented by an ephemeral per-run pipe + in-stream credential + the guest's inability to
enumerate host pipes.

If a later PoC shows the mapped pipe does **not** hold (e.g. the guest can reach other host pipes, or the channel can't
be credentialed), the remaining realistic Windows options are: **(a) a Fusion-managed dedicated Hyper-V micro-VM** (full
VM we own, HvSocket raw at the VM boundary where it is supported - heavier, our own image lifecycle), or **(b) HARD
declared UNAVAILABLE on Windows for v0.6** (ship CONFINED: FS + process + env OS-enforced; network boundary documented as
not-HARD). Do **not** auto-fall-back to l2bridge.
