# v0.3 — adaptive multi-agent orchestration

Fusion no longer picks one fixed pipeline when a task starts. During a read-only task it gathers evidence from several
independent, bounded investigations (in parallel where that pays off), compares it, and escalates or stops under a
host-enforced budget. Control returns to the lead without any model gaining authority.

**Models propose. Fusion verifies. Humans approve.** A routing decision is a proposal the host reads strictly and
authorizes or refuses. Nothing in this milestone can write, widen a view, add a partner, raise a budget or reach the
Writer route. Changes still go only through the existing confirmed build route.

## The adaptive route (state machine)

```text
start ─ single ───────────────────▶ ANSWER ─ completed ────────────────────────────────▶ finish (answered)
  │                                   └─ failed: turn limit, escalation allowed ─▶ DECIDE(plan)
  └─ team / verify (an explorer with a PROVEN read-only posture, budget for one investigation) ─▶ DECIDE(plan)
DECIDE(plan)      answer ─▶ ANSWER │ delegate ─▶ INVESTIGATE │ refused or failed ─▶ INVESTIGATE (Fusion's areas)
INVESTIGATE       transient failures and retry budget ─▶ INVESTIGATE (a repeat, once per investigation)
                  evidence sufficient ─▶ SYNTHESIZE (the lead reclaims the task)
                  evidence weak, budget for another batch ─▶ DECIDE(evidence)
                  evidence weak, no budget ─▶ SYNTHESIZE (incomplete: what is supported, what remains unknown)
DECIDE(evidence)  synthesize ─▶ SYNTHESIZE │ delegate ─▶ INVESTIGATE │ stop ─▶ finish (stopped, no conclusion)
                  refused or failed ─▶ SYNTHESIZE
SYNTHESIZE        completed ─▶ REVIEW (a delegated route, a fresh reviewer, budget) │ finish │ failed ─▶ finish (failed)
REVIEW            ─▶ finish (answered)
any step the budget refuses, or the route's deadline ─▶ finish (stopped: budget exhausted)
```

The host classifies each shell line before any model runs:

- **single**: a question, an explanation, a narrow analysis, or any analysis of a small project. One lead turn.
  (`ask` turns, such as "what does package.json do?", stay a single conversational turn: `Route: lead only`.)
- **team**: a broad analysis of a large project (more than 150 inventoried files). The lead decides, and may still
  answer directly.
- **verify**: a read-only line that asks whether ONE earlier finding holds ("is that really a bug?", "check whether the
  first finding is true"). The finding is the host's claim; the lead cannot substitute its own.

A single answer that fails with a **turn limit** (the provider's own stop, a provider-neutral `failureCategory`) is
evidence the task is larger than one turn. It escalates once to a lead decision, when an explorer is proven and the budget
allows a decision, one investigation and the synthesis. No other failure escalates.

## Contracts

**Routing decision** (the lead, one JSON object, raw or in one outer json fence):

```json
{"action":"answer"}
{"action":"delegate","investigations":[{"area":"src","question":"Where is a turn routed?"}],"claim":"optional, team routes only"}
{"action":"synthesize"}
{"action":"stop"}
```

- Read against the rules of that moment: the allowed actions (`answer`/`delegate` when planning;
  `synthesize`/`delegate`/`stop` after evidence), the closed list of areas, the investigation count the budget leaves,
  and whether a claim may be named.
- Refusal categories: `empty reply`, `oversized reply`, `invalid JSON`, `prose around the JSON`, `more than one JSON
  value or fence`, `malformed fence`, `schema mismatch`, `unknown action`, `action not allowed now`, `no
  investigations`, `too many investigations`, `unknown area`, `withheld area`, `duplicate area`, `question too long`,
  `claim too long`, `claim not allowed`.
- Nothing is repaired but an area id's spelling (`src/`, `./src`).

**Investigation packet** (the host, per explorer). It holds only what the explorer needs:

- the packet id, batch and attempt;
- the area and its inventoried file count, and key files from Fusion's inventory;
- the question, and the claim to judge (if any);
- validated findings of earlier batches about that area (the claims only, never text around them);
- the file budget (4).

No lead reasoning, no other explorer's report, no transcript, no session.

**Investigation report** (the explorer, one JSON object):

```json
{"status":"answered|inconclusive","verdict":"supported|contradicted|unclear","summary":"…",
 "findings":[{"claim":"…","paths":["relative/path"]}],"openQuestions":["…"],"contradictions":["…"]}
```

- Bounded everywhere: a summary of 1,500 characters, at most 8 findings of 280, at most 6 paths each.
- Paths are relative and clean (no absolute path, `..`, backslash or URL).
- A verdict is required when the packet carries a claim.
- The host checks every cited path against the view it shared: only those count as cited evidence.
- A reply that is not a valid report is kept as an **unstructured** report: bounded, marked, and used as untrusted text.

**Synthesis evidence** (the host, for the lead's reclaim):

- each investigation's validated report, or its safe failure;
- Fusion's assessment: counts, cited files, and a `CONFLICT:` line when verdicts disagree, which tells the lead to
  compare the cited evidence and never invent a consensus;
- the areas no report covers.

**Evidence assessment** (the host). The evidence is **sufficient** only when every investigation reported with at least
one cited shared file and the verdicts agree. Otherwise it is weak, and the host names why: `failed investigations`,
`inconclusive reports`, `conflicting verdicts`, `uncited reports`, `no reports`.

## Parallelism

- A batch runs at most `maxConcurrentInvestigations` (3, also the hard cap) at the same time, started in order.
- Each investigation runs in its **own view copy** (`ProviderViewStore.replica`: the already filtered view copied into
  a fresh owned root with its own identity). The source must be intact before and after the copy, and the copy must match
  it file for file.
- Each investigation also gets its **own fresh provider session**. No transcript is shared, and no workspace is shared
  or mutable.
- After each turn the copy must still equal its identity, and the primary must be unchanged. Otherwise the conversation
  closes with a security stop.
- Every investigation has a time budget (6 minutes by default, and never longer than the route has left). A timed-out
  turn is aborted and reported as a retryable `timeout`; its siblings continue.
- A **fatal** failure of any investigation (a security violation, an internal error, an item that does not settle within
  its grace after abort) aborts every sibling. The batch waits for all of them to settle, then rethrows.
- The user's cancellation (Ctrl+C) aborts every investigation. The batch waits for them, and the shell reports
  `Cancelled. Nothing was changed.`
- A batch never returns before every started investigation has settled. Each one closes its session first (its process
  has ended), then removes its view copy. `RepositoryConversation.close()` aborts and awaits every investigation still
  running.
- The fresh critique is also an isolated turn (its own copy and session), and sees only the bounded synthesis and
  Fusion's coverage facts.

## Budgets

| Budget | Default | Hard cap |
| --- | --- | --- |
| Concurrent investigations | 3 | 3 |
| Investigation batches | 2 | 3 |
| Delegated investigations (repeats excluded) | 5 | 8 |
| Repeats of failed investigations (once each) | 2 | 3 |
| Lead turns (answers, decisions, syntheses) | 4 | 6 |
| Reviewer turns | 1 | 2 |
| Model turns in the route | 10 | 16 |
| One investigation | 6 min | 15 min |
| The route | 20 min | 45 min |

- Overrides (`routeBudget`) are validated integers within [minimum, hard cap]. Anything else is refused, never clamped.
  The budget comes from the host only: no model reply has a budget field.
- Every turn is **reserved before it starts**, all or nothing. A delegation always keeps back the lead's synthesis and a
  delegated route's fresh review.
- A lead decision is only offered when the budget still allows at least one investigation after it.
- When a budget is exhausted, the route stops cleanly: `Fusion stopped before drawing a conclusion: the route's budget ran
  out (<budget>)`. Fusion shows what the investigations reported, marked as untrusted, and draws no conclusion from it.

## Failure semantics

| Situation | Behaviour |
| --- | --- |
| The lead's planning decision is malformed, unknown, oversized, asks for too many investigations or for an unknown or withheld area | Refused with its category; Fusion's own areas (never a withheld one) are investigated; the terminal says so |
| The planning turn fails | The same fallback, with the safe failure detail |
| One investigation fails transiently (timeout, process or protocol failure) | Repeated once within the retry budget; siblings' reports stand |
| One investigation fails for good (authentication, posture) | Never repeated; reported with its category; the evidence is weak |
| Every investigation fails | The lead reclaims without reports (or reviews the gap first when the budget allows); the answer is marked incomplete |
| Conflicting verdicts | Weak evidence; the lead may ask for more; the synthesis gets a `CONFLICT:` instruction; the terminal shows `Conflict: …` |
| An evidence decision is refused or fails | The lead reclaims with what exists |
| The lead decides `stop` | No conclusion; the investigations' reports are shown as unconfirmed findings |
| A budget is exhausted, or the route's deadline passes | Clean stop, honest incomplete result |
| A provider writes into its view copy, or the primary changes | Security stop: siblings aborted, every copy removed, the conversation closed |
| The user cancels during a batch | Every investigation stopped and cleaned up; nothing changed; the shell continues |
| A failed required security gate (posture, authentication) | Never downgraded: an unproven explorer is never used; a failed posture check fails that turn |

## Observability and metrics

Every analysis prints its route and turns:

```text
  Route: lead decision → 3 parallel investigations → lead synthesis → fresh review
  Turns: 6 model turns (lead 2 · explorers 3 · reviewer 1) · 1 batch (1 parallel) · 41 s
```

Other routes read `lead only`; `lead decision (refused: unknown area) → Fusion's own areas → …`; `… → 2 repeats (1
failed) → lead evidence review → …`; `lead answer (failed: turnLimit) → escalated (turn limit) → …`; `… → stopped (budget
exhausted: model turns)`. The trace holds roles, providers, transition categories, counts, durations, failure categories
(for investigations: one per failed investigation of each batch and repeat) and cited-evidence counts, never model text or
reasoning.

Every failed investigation attempt is shown with its safe category and Fusion's own message, including one a repeat
superseded:

```text
  Explorer investigations: 3 of 3 answered (src/ by reviewer (meta), test/ by reviewer (meta), docs/ by reviewer (meta))
  (explorer for src: attempt 1 failed — provider failure: Muse Exec reported a failed turn. It was repeated once and answered.)
```

A failed Muse turn also says, safely, how it ended. The reason is read in memory and never kept; the detail holds only
Fusion's labels and counts:
- `reason_class`: `stepLimit`, `contextOverflow`, `http429`, `http5xx`, `network`, `timeout`, …, `unclassified` or `absent`;
- `reason_chars`: the reason's length;
- `events`: the protocol events the turn emitted, counted by type;
- `max_model_steps`: the step limit it ran under;
- `prompt_chars`: Fusion's own prompt size;
- `text_chars` and `exit_code`.

A step limit, an oversized input or a rate limit also becomes the turn's category (`turnLimit`, `inputTooLarge`,
`rateLimited`). For example:
`(explorer for test failed: turnLimit: Muse Exec reported a failed turn. (reason_class=stepLimit reason_chars=41
events=run.lifecycle.started:1,run.model.configured:1,run.model.step:4,run.terminal.failed:1 max_model_steps=4
prompt_chars=2310 text_chars=0 exit_code=0))`.

**Local metrics.** The per-project session metadata (schema version 2; version-1 files still read) adds safe counts of
every route:

- routes and model turns;
- lead, explorer and reviewer turns;
- batches and parallel batches;
- repeats and failed investigations;
- lead reclaims, escalations, fallbacks and budget stops;
- duration.

`history` in the shell prints them. There is no remote telemetry, and no prompt or reply is stored for metrics.

## Session continuity

`analyze → explain the first finding → is that really a bug? → fix it` works with host-owned state only:

- the analysis's bounded findings;
- the finding in focus;
- the host's evidence about a verified finding: the cited shared files and verdict counts, never text.

**The findings** are the answer's own `Findings:` list, and only it: its last occurrence, up to where another section
starts. A prose `## Problems` heading, a numbered "Suggested fixes" list or the proposed build task never becomes a
finding. Their numbers are the numbers the user sees.

**Selecting a finding** is deterministic and never a guess:
- **By position:** "the first finding", "finding 3", "the last one".
- **By pronoun:** "is that really a bug?" means the finding in focus.
- **By its distinctive terms:** "is the trusted_proxies finding really a problem?" names the one finding that carries
  every identifier-like term the line names (`trusted_proxies`, `configuration.yaml`, a path's file name). Whole tokens
  only, never a substring.
  - **Several findings match:** Fusion lists them and asks which one.
  - **None matches:** Fusion says so and asks.

  Either way no model turn runs, nothing is replaced, and nothing falls back to the first finding or to a proposal. A
  finding named this way becomes the active one, and "fix it" then means exactly that finding. While a finding is
  active, the analysis's broad proposed build task is not used.

The lead's own history holds its answers and syntheses, never an explorer's report. A verification keeps the analysis's
findings, so "fix it" still means the verified one. Its task carries the verification's host-checked evidence, which
helps the lead choose the file scope:
- `(Fusion's investigation of this finding cited: …)`: the shared files the investigations' reports cited;
- `(Fusion's verification of this finding cited: …)`: when the lead verified the finding itself (`lead decision (answer
  directly) → lead answer`), the shared files its verification answer cited. These are the files the verification's
  coverage line reports as cited.

Only files Fusion found in the shared copy count, and never the verification's text: it is model output, and the
finding the human confirms stays the analysis's own. The change then goes through the **existing** route: bounded scope,
read-only Change Author, validated ChangeSet, private candidate, confined verification, review where required, immutable
delivery, explicit approval, checkout-bound apply.

## Muse explorer posture (B8)

The installed Muse runtime is validated only for the **Reviewer** binding: 1.4.0-R4161.1 by O5.5B24, and 1.4.0-R4302.1
(Muse's own update of 2026-09-27) by V0.3-R4302 — each by recorded evidence of an authorized live pass for exactly that

approval, personal-context and extension controls read `unknown` (`fusion doctor`). Muse has no model-free canary that
could prove them. They cannot be proven mechanically here.

v0.3 therefore keeps the safe fallback: the Explorer binding is **not** marked validated, and the validated Reviewer
binding serves as the exploration transport, in a separate context per investigation. Every route that delegates says so
on the terminal. Validating the Explorer binding needs its own authorized live probe and a recorded validation. That is
not part of this milestone.

### First real run (2026-09-28): L1 PASS, L2 FAIL, L3 PASS, L4 FAIL — diagnosed

The maintainer's run went all the way through the real providers and the full mutation path (Docker verification, delivery,
human approval, apply, `V0_2_1_LIVE_BUILD_PATH: PASS`, no sentinel). Both failures were diagnosed from the transcript and the
code before anything changed.

- **L2** (`3 parallel investigations (2 failed) → 2 repeats → lead synthesis → fresh review`, `3 of 3 answered`, clone
  unchanged). The product did what this document specifies: two transient failures were repeated once and answered, and
  the synthesis and the fresh review followed. The FAIL came from the runner, whose pattern required
  `parallel investigations → `. That pattern could never accept the documented `(2 failed) → 2 repeats`. The runner now judges the
  route contract (`scripts/v03-live-verdicts.mjs`): a bounded recovery passes; an investigation that never answered fails.
  - **The failures' category was not recorded anywhere.** The terminal showed only each investigation's final state, the
    trace kept counts, and the session metadata keeps counts. That contradicts "the trace holds … failure categories".
  - **What code and timing do establish:** only a retryable process, protocol, output or start failure is repeated, so it
    was not authentication, posture, security, cancellation, an internal error or a budget stop. The whole route took 191 s
    against a 180 s provider limit and a 6-minute investigation budget, so it was not a timeout.
  - **Now:** the trace keeps one category per failed investigation, and the terminal prints each failed attempt with its
    category and Fusion's safe message, so the next run shows it.
- **L4** (`evidence=NO`, everything else yes). The lead verified the trusted_proxies finding itself (`lead decision (answer
  directly) → lead answer`), citing `configuration.yaml` and `home-assistant.log`. The session remembered evidence from
  investigations only, so "fix it" carried the analysis's finding and nothing of its verification. That is a product
  defect in the analysis → verification → fix handoff. The task now carries `(Fusion's verification of this finding cited:
  …)`, and the runner checks that it names the verified finding and exactly the files that verification cited.

### Second real run (2026-09-28): L1 PASS, L2 FAIL, L3 PASS, L4 FAIL — diagnosed

- **L2** (`… (1 failed) → 1 repeat (1 failed) → lead evidence review (refused: question too long) → …`, `2 of 3 answered`).
