# v0.6 — hard isolation and resilience (design)

**Status: released in v0.6.0** (PRs #42–#70 and the release fix B1); not published to npm. This document is the design
as it was built, PR by PR. A capability counts as shipped and validated only where its invariant row in
[the v0.6 matrix](v0.6-invariant-matrix.md) is COVERED and its live evidence is recorded. What v0.6.0 does not provide
is listed in the [release notes](release-v0.6.0.md#known-limitations).

> What O6 Phase 2 proved, and what stays open, is in [the O6 Phase 2 closeout](v0.6-o6-phase2-closeout.md). Unattended
> Writer mode stays BLOCKED.

## Thesis

v0.5 kept: **Models propose. Fusion verifies. Humans approve.** v0.6 adds three sentences and makes them
mechanically true:

- **Untrusted execution is capability-bounded** — the operating system, not a prompt or a flag, denies what a
  provider/candidate process may not do.
- **Durable work survives interruption** — a crash does not erase Fusion's knowledge of what completed.
- **Irreversible actions are never blindly replayed** — an interrupted apply is recognised as an interrupted
  transaction, not mistaken for success or restarted from memory.

The objective is not "Fusion never crashes". It is: providers may fail, processes may die, the host may restart —
and Fusion can still determine what is known, what completed, what is safe to resume, and what must stop for a human.

## No security theater

A boundary is called **hard isolation** only when the operating system (or an equivalent trusted isolation backend)
denies the operation even if the sandboxed program deliberately tries to violate policy. Prompts, provider
permission settings, tool descriptions and in-process path checks are not hard isolation. HARD requested with the
backend unavailable **fails closed** — it never silently runs unsandboxed.

## Posture states

| Posture | Meaning |
| --- | --- |
| `HARD` | Filesystem, network and process-tree boundaries are all OS-enforced (each mechanically proven by a probe). |
| `CONFINED` | Filesystem and process-tree are OS-enforced; the network is not provisioned (e.g. no `fusion sandbox install`). |
| `UNAVAILABLE` | No OS backend can enforce the required boundaries here. |

`bestEffort` (read-only, non-mutating local work) may proceed under any posture but never reports `HARD`.

## Threat model (honest)

The sandboxed provider/candidate process is assumed hostile: it may ignore instructions, be prompt-injected, spawn
arbitrary children and grandchildren, attempt path traversal / alternate path forms / reparse points, try to read
host credentials, other candidates, other projects or Fusion's own state, attempt unauthorized network connections,
leave orphan processes, or crash. The backend must contain all of that at the OS level.

The sandbox does **not** defend against kernel compromise, an administrator/SYSTEM compromise, or a malicious
physical administrator, and it cannot audit what a provider vendor does with the context a session reads. Those are
out of scope and stated as such.

## Backend

v0.6 selects an OS-enforced Windows backend behind a `SandboxBackend` abstraction and a capability probe:

- **AppContainer (LPAC) + explicit filesystem grants + a kill-on-close Job object** — the primary path; needs no
  administrator for filesystem and process-tree enforcement. A per-execution AppContainer profile gives each
  candidate its own identity, so sibling candidates are mutually inaccessible.
- **`CreateProcessInSandbox` (`processmodel.dll`, Microsoft's Win32 app-isolation path)** — used opportunistically
  where the OS exports it and a probe passes; the OS builds the token and applies a bound filesystem, so there is no
  host-ACL bookkeeping. The API is experimental and is treated as such.

The **network boundary** (deny-all by default, otherwise a narrow allowlist) and loopback exemption require a
**one-time administrator provisioning step** (`fusion sandbox install`); runtime execution stays unelevated. Windows
Sandbox (a Hyper-V VM) was evaluated and rejected as the per-candidate backend (feature disabled by default, one
instance at a time, heavy startup).

## Capability manifest

Every untrusted execution is bound to an immutable, hashed **capability manifest**: its backend and sandbox
identity, the exact host paths it may read/write and those denied, its network policy, the environment variable
*names* it inherits (never values), its process and resource limits, timeout and working directory. A model may
*request* a capability; it may not *grant* one — the manifest is built from host policy, never from model output.

## Durable execution and recovery (design)

- An append-only, hash-chained **run journal** records every security/reliability-critical transition durably before
  the irreversible action it precedes. Truncation, sequence gaps, duplicate sequence, a broken hash chain, a
  snapshot/journal mismatch or an unsupported schema make the journal `JOURNAL_CORRUPT` / `RECOVERY_REQUIRED` — a
  corrupt security-critical log is never guessed through.
- Bounded **checkpoints** snapshot derived state; the journal stays authoritative. Startup loads the newest valid
  checkpoint, verifies it against the journal, replays the rest and classifies interrupted operations.
- A real **single-writer** lease (a random execution-instance nonce, not a bare PID) prevents two Fusion processes
  from mutating one run; a second writer gets `RUN_ALREADY_CLAIMED`. Read-only inspection stays possible.
- Interrupted operations are classified `SAFE_TO_REPLAY` / `SAFE_TO_RESUME` / `REQUIRES_REVALIDATION` /
  `REQUIRES_HUMAN` / `BLOCKED`. `UNKNOWN` never becomes safe automatically.
- The **recoverable apply transaction** runs `PREPARED → CLAIMED → APPLYING → VERIFYING → COMMITTED`, with
  `ROLLBACK_REQUIRED → ROLLING_BACK → ROLLED_BACK` and `RECOVERY_REQUIRED` where recovery cannot be proven safe.
  This is a durable, recoverable, journaled local apply — not full multi-file ACID, and it is not described as such.
  Rollback material that may contain secrets lives in a host-owned recovery vault, never in a normal log.

## Compatibility

All v0.1–v0.5 semantics are preserved (tournaments, evidence graph, proof obligations, falsifier, verification mesh,
delivery, human approval, apply). Hard isolation and durability surround these mechanisms; they do not replace them.
Historical runs remain inspectable and may honestly show `LEGACY_NON_RESUMABLE`; old runs are never fabricated into
resumable ones.

## The AppContainer backend (PR B)

The native launcher lives in `native/fusion-sandbox/` and is built with the in-box .NET Framework x64 compiler — no SDK,
no NuGet, no network:

```powershell
powershell -File native/fusion-sandbox/build.ps1   # writes the git-ignored native/fusion-sandbox/bin/fusion-sandbox.exe
```

The host (`src/platform/isolation/appcontainer-backend.ts`) locates and SHA-256-hashes the launcher, runs its canary
self-test in a disposable directory, validates the returned `ConfinementProof` against that hash and a clock window, and
maps the mechanically-observed facts onto the provider-neutral posture probe. The launcher creates a per-execution
AppContainer (no capabilities) with explicit read/write DACL grants inside a kill-on-close Job with handle-list-limited
stdio and an explicit environment; the child is created suspended, assigned to the Job, then resumed, so restrictions are
in force before its first instruction.

**Validation.** Deterministic host-mapping tests run in CI (`test/v06-appcontainer.test.ts`). The real OS enforcement is
proven by the opt-in Windows integration test `test/live/appcontainer.live.test.ts` (maintainer-run, like the Docker live
suite; not in CI): it asserts every confinement fact under real OS denial — granted read/write work; ungranted, sibling,
registry-secret and loopback-network access are all denied; a spawned descendant is captured by the Job; a timeout
terminates the tree; and cleanup leaves no lingering grant. First passing run: 2026-09-29 on Windows 11 Pro 25H2 (26200),
unelevated. A fake adapter is never accepted as evidence for HARD.

Network **allowlist** egress (WFP scoped to the package SID) and its loopback exemption need one-time administrator
provisioning and are a later milestone; the no-capability AppContainer already enforces deny-by-default network.

## Delivery plan

PR A — contracts (this PR): capability manifest, posture states, network policy, durable/recovery/transaction state
machines, typed isolation and recovery states, schema/versioning. Pure, provider-neutral, unit-tested.
PR B — AppContainer backend, native launcher, `fusion sandbox doctor/install/uninstall`, filesystem + process-tree
enforcement with real-OS canary tests. PR C — network boundary, environment/credential minimization, per-candidate
sibling isolation. PR D — durable hash-chained journal and single-writer nonce lease (landed:
`src/platform/durability/journal.ts`, `lease.ts`; checkpoints and replay follow in D2/E). PR E — recovery planner,
resume, pending human gates, provider-step durability. PR F — recoverable apply transaction, recovery vault,
idempotency. PR G — adversarial + crash-injection suites, invariant matrices. PR H — live acceptance runner, docs,
observability, final audit.
