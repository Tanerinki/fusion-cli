## 4. Checkout byte stability (Windows `core.autocrlf`)

**The defect.** With `core.autocrlf=true`, a clean Windows checkout of an LF blob has CRLF working bytes. Those bytes do
not match the manifest's preimage, which is taken from the blob. So the apply refused, correctly.

**The refusals.** Run `r-00muuaiy5m-c30772724e473f3a323ed4c0efcc804b`, delivery `d-d33c08c48295c44ff2dd3c91`:

- `approved`, then `precheckFailed [fileChanged: src/sum.mjs]` at 2026-10-05T00:04:09Z;
- a second attempt, `precheckFailed [dirtyTree]`, at 00:07:40Z;
- **no `claimAcquired` and no apply event**: Fusion mutated nothing during either refusal (LIVE-RECORDED).

**The fix.** `cdfbaaf` (2026-10-05T02:50:42Z) added checkout byte-stability assessment:

- a build whose in-scope paths would be transformed by the checkout is blocked before it starts, with
  `checkoutByteTransform` (no model turn);
- an apply refusal caused only by line endings is reported as `fileChanged` with an EOL-only diagnostic;
- covered by `test/v06-checkout-stability.test.ts` (DETERMINISTIC).

**After the fix.** The fresh byte-stable disposable checkout of section 3 was prepared at 03:14:09Z and applied at
03:20:45Z, after the fix (LIVE-RECORDED).

**Correction in final review (`aaca592`, 2026-10-09).** The confirmation step decoded `git cat-file` output as UTF-8
text. A non-UTF-8 committed blob, or one over the 32 MiB Git output cap, made it fail, and the failure was read as "not
in HEAD", i.e. byte-stable. A Latin-1 file genuinely CRLF-smudged by `core.autocrlf=true` therefore passed this early
gate. The applier's raw-SHA-256 precheck still refused before any write.

The comparison now uses Git object IDs: `ls-tree` for the committed blob, and `hash-object --no-filters` for the raw
working bytes. Any Git failure, or a non-regular committed entry (a symlink or submodule), is `undetermined` and refused
(DETERMINISTIC).

## 7. Process-tree hardening (security)

Commit `5ea1bc5` (2026-10-08). DETERMINISTIC, plus real Windows process-tree tests with the production inspector.

**Ownership**

- A process is owned only if it is linked to an owned process **and** was created no earlier than it. A stale Windows
  `ParentProcessId` that names a reused Fusion PID no longer establishes ownership.
- Every adopted process needs a valid creation/start identity. A missing, zero or unparseable identity is never adopted
  and never killed; where it links into the tree, cleanup fails closed.
- The root must be listed exactly once with a valid identity, while the root is still alive. A root that exited before
  its listing completed never identifies children.
- Unrelated stale-parent processes are never adopted and never passed to `kill`
  (`test/v06-process-termination.test.ts`, the `v0.6 term F1` tests).

**Retry policy**

- Positive evidence of a survivor refuses at once, at `attempts=1`, before any model turn:
  - the root did not exit: `process_survived`;
  - an owned descendant survived: `descendant_survived`.
- Only cleanup ambiguity gets the one bounded repeat: `tree_uncaptured`, `tree_unverified`. A second ambiguous cleanup
  refuses at `attempts=2`.
- A taskkill exit code is never part of the verdict.
- These labels are now the authoritative cleanup labels. A tree terminator can no longer self-report a cleanup verdict
  (`cleanupError?: never`).

**Remaining limitation (explicit).**

- A descendant spawned and orphaned from the owned set inside the final kill window can escape.
- A member whose PID is reused between the kill path's re-listing and its signal could be missed.
- Windows creation times are wall-clock values.
- Only a Windows Job Object (kill-on-close, the HARD path) gives a hard OS-level guarantee.

**Behaviour change.** A process that exits on its own during the cancellation grace, before its listing completes, now
reports `tree_uncaptured` (fail closed).
