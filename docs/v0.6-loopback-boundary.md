# v0.6 — I14: broker-only loopback boundary (Windows enforcement limitation)

**Status: NOT PROVEN — genuine Windows enforcement limitation. HARD is NOT claimed for the broker-only network boundary.**

## The requirement

For a HARD provider execution the sandboxed AppContainer should reach **only** the Fusion broker on loopback, and no other
`127.0.0.1` service. The intended enforcement: bind, at the network layer, `(package/AppContainer SID) + (loopback) +
(exact broker port)` and deny every other loopback destination — mechanically verified, not inferred from rule presence.

## The finding (investigated, not guessed)

Per-port loopback restriction for an AppContainer package SID is **not achievable with the AppContainer + LoopbackExempt
design via any supported Windows mechanism**:

1. **`CheckNetIsolation LoopbackExempt` is per-package, all-or-nothing.** It adds a package SID to the loopback exemption
   list; there is no port granularity. An exempted AppContainer may reach ANY `127.0.0.1` port, not only the broker. It is
   also explicitly a development aid, not a production security control.
2. **The Windows Firewall / WFP does not filter loopback traffic.** Loopback (`127.0.0.1`, `::1`) is short-circuited and
   does not traverse the ALE filtering pipeline where a `New-NetFirewallRule -Package <SID> -RemotePort <n>` condition
   would be evaluated. A package-SID-scoped firewall rule that names a loopback remote port therefore does **not** enforce
   — it is present but inert for loopback. (Block-wins precedence would also defeat an allow-one/deny-rest shape even if
   loopback were filtered.)
3. **Only a kernel WFP callout driver** at the loopback-capable layers could inspect an AppContainer's loopback
   connections and filter by port — a signed kernel driver, out of scope for v0.6, and not a supported user-space rule.

Because of (1)–(3), Fusion does **not** ship a firewall rule that claims to enforce broker-only loopback: that would be
security theater. `BROKER_ONLY_LOOPBACK_BOUNDARY = NOT_PROVEN`, `UNRELATED_LOCALHOST_ACCESS = ACCESSIBLE`.

## What IS enforced (and the residual)

- **OS-enforced (HARD):** filesystem confinement, process-tree containment, environment minimization, and **DENY_ALL
  direct network** (the no-capability AppContainer has no network at all until a loopback exemption is added).
- **Application-layer (broker):** once the loopback exemption is added, the broker enforces the exact FQDN + port allowlist
  and a per-run credential (I12), so a *different* local process cannot reuse the broker's authority, and the broker will
  not proxy off-allowlist.
- **Residual (NOT closed):** the exempted AppContainer can open a **direct** socket to an unrelated `127.0.0.1` service,
  bypassing the broker entirely. The per-run credential does not prevent this. On a machine running other unauthenticated
  localhost services (dev databases, other dev servers), an untrusted provider could reach them. This is release-critical
  for the *network* dimension of HARD.

## Mechanical verification the maintainer can run (to confirm, not infer)

With the native launcher built and an elevated shell (the exemption add is admin-only):

```powershell
# 1. two disposable local listeners: pretend broker + an unrelated service
#    (e.g. two `node -e "require('net').createServer().listen(<port>,'127.0.0.1')"` processes)
# 2. add the loopback exemption for a throwaway AppContainer SID (admin), then run, inside that AppContainer, a child that
#    attempts TCP connects to BOTH ports and a direct socket bypassing HTTPS_PROXY:
#      broker-port     => EXPECTED reachable
#      unrelated-port  => if reachable, the boundary is NOT enforced (this finding); if refused, enforcement exists
#      direct socket   => if reachable, the provider can bypass the proxy
# 3. remove the exemption (admin).
```

The expectation, from (1)–(3) above, is that the unrelated port **is** reachable — i.e. the boundary is not enforced. Run
it to confirm on the target machine; do not infer HARD from rule presence.

## Options (maintainer decision — this is where v0.6 stops)

None of these is applied autonomously; each changes the security model or is out of v0.6 scope:

1. **WFP callout driver** (kernel, signed) to filter AppContainer loopback by port — closes the residual; large, out of
   v0.6 scope.
2. **A different sandbox network model** (e.g. a network compartment / namespace, or a non-loopback IPC the provider's
   HTTP client can proxy through) — closes the residual; a redesign.
3. **Accept the residual with compensating controls** — the per-run broker credential (done) plus an explicit operator
   precondition that no untrusted localhost services run during a HARD provider turn. This is a **documented limitation**,
   NOT "HARD network isolation", and must be labelled as such — never called HARD.

## Consequence

Per the program ("do not call the posture HARD for broker-only loopback unless the intended boundary is mechanically
demonstrated"; "do not weaken the definition to finish v0.6"), the HARD **network** boundary is **not met**. Filesystem,
process, environment and DENY_ALL-direct-network HARD are intact and proven; the broker-only egress property is not.
**READY_FOR_GATE_2 = NO** until option (1) or (2) lands, or the maintainer explicitly accepts option (3) as a labelled
limitation. Fusion stops here for that decision.
