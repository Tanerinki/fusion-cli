# v0.6 — network-isolation architecture spike (broker-only egress under HARD)

**Status: SPIKE / evidence + recommendation. No large backend implemented. This is a stop for a scoping decision.**

## The invariant to satisfy (unchanged, not weakened)

Under HARD, the untrusted provider may communicate with **exactly the Fusion egress authority its run needs** AND cannot
open a direct connection to arbitrary localhost services, LAN services, or arbitrary Internet hosts. An application-layer
broker credential is **not** equivalent to an OS-enforced network boundary. Must not trade away the existing OS-enforced
filesystem / process-tree isolation to obtain the network boundary.

Established (I14, `v0.6-loopback-boundary.md`): with the AppContainer + broad `LoopbackExempt` design the boundary is NOT
enforceable — LoopbackExempt is per-package (all-or-nothing) and the Windows Firewall does not filter loopback.

## Option A — packaged-peer loopback (provider package A → broker package B only)

**OPTION_A_PACKAGED_PEER = NOT_FEASIBLE** (via supported user-mode mechanisms).

reason= Windows exposes exactly one supported per-package loopback control: `CheckNetIsolation LoopbackExempt`, which is
binary per package SID — there is **no supported "package A may reach package B's loopback endpoint only" rule**
(no `LoopbackAccessRule` API; `New-NetFirewallRule -Package` does not filter loopback). The default AppContainer
loopback *block* is a WFP network-isolation decision, but once a package is exempted, loopback is not further filtered by
supported firewall rules. Constraining A→B specifically would require **custom WFP filters/callout at the loopback-capable
layers** — i.e. kernel-driver territory, which the decision rules out for v0.6 unless everything safer is ruled out first.
Even then it is NEEDS_PROOF, not a supported configuration. Additionally, exempting the provider package at all reintroduces
broad loopback reach, which is the residual we are trying to remove. Not pursued.

## Option B — ACL-bound IPC broker (named pipe / ALPC, DACL scoped to the exact AppContainer SID)

**OPTION_B_ACL_IPC = NOT_FEASIBLE** (for the real provider HTTP stack, via supported configuration) — sub-parts NEEDS_PROOF.

reason= The IPC endpoint side is strong: a **named pipe (or ALPC port) with a DACL granting exactly the provider's
AppContainer SID** is OS-enforced, per-identity, needs **no** loopback exemption and **no** network capability — the
provider could reach only the one pipe granted to its SID, and nothing else on localhost, LAN or Internet. That side
cleanly satisfies the invariant. The blocker is the **provider transport**: the boundary exists only because the real
provider (`claude.exe`, muse) needs a **TCP** egress proxy (`HTTPS_PROXY=host:port`). Its HTTP stack cannot be pointed at a
named pipe / ALPC endpoint through any supported configuration (`HTTPS_PROXY` expresses only a TCP URL; the packaged binary
cannot have a custom HTTP agent / `socketPath` injected). An in-sandbox **TCP→pipe adapter** would reintroduce a TCP
listener on the **host** loopback namespace (AppContainers share the host loopback), i.e. the exact unrestrictable-loopback
problem again — and reaching even that adapter needs the broad exemption. So B is viable ONLY if a provider runtime natively
supports a non-TCP (pipe/socket) proxy transport — NEEDS_PROOF against the actual runtimes, but standard Claude/Muse do
not. Not viable as the general HARD network path.

## Option C — isolated network backend (untrusted provider in a network-isolated worker)

**OPTION_C_ISOLATED_NETWORK_BACKEND = NEEDS_PROOF** (feasible in principle; the only direction that satisfies the invariant
without a kernel driver).

reason= Move ONLY the untrusted provider execution into a worker with its **own network namespace** — a Hyper-V isolated
container / utility VM, an isolated Windows container, or a WSL2/VM worker. There, loopback is the worker's OWN isolated
loopback (not the host's), and egress is enforced at the **worker's virtual NIC** (host vNet/firewall on the vSwitch, or the
namespace's own policy) — so "reach only the Fusion egress authority; deny arbitrary localhost/LAN/Internet" becomes an
OS/hypervisor-enforced network-namespace policy, no kernel callout driver required. The trusted Fusion control plane and the
broker stay on the host; only the provider process moves. This is the architecture that mechanically satisfies the network
invariant with supported mechanisms. It is NEEDS_PROOF (not PROVEN) because: (a) the exact egress-restriction mechanism must
be mechanically verified on the target (disposable-listener canary from inside the worker: broker ALLOWED; unrelated
localhost/LAN/Internet DENIED); and (b) it is a real backend with cost (image/base, startup latency, resource use) and it
**changes the filesystem/process isolation mechanism** — the current per-execution AppContainer FS grants + kill-on-close
Job would be replaced by the worker's file-sharing + the worker boundary, which must be proven to preserve (not weaken) the
existing FS/process HARD isolation. That preservation is the main risk to retire before implementing.

## Recommendation and stop

No supported **user-mode** design is **PROVEN** viable from analysis alone: A and B are NOT_FEASIBLE for the real provider,
and C — the recommended direction — is NEEDS_PROOF (it requires a real-Windows mechanical proof of both egress restriction
and preservation of the existing FS/process isolation, and it is a substantial backend). Per the decision's own rule
("continue autonomously after the spike only if one design is clearly proven viable; if none can prove the boundary, STOP
with evidence; do not silently select the residual"), Fusion **stops here** with this evidence rather than implement a large
Option-C backend on an unproven foundation or fall back to the residual.

Proposed smallest next step (needs approval, as it is a real backend + a real-OS proof): a **bounded Option-C proof-of-
concept** — run a trivial fake provider in one candidate isolated-worker technology, and mechanically verify with disposable
listeners that (broker ALLOWED; unrelated localhost / LAN / Internet DENIED) AND that the worker still enforces the
view(ro)/scratch(w)/deny-the-rest filesystem boundary and process-tree kill. Only if that PoC passes does the full Option-C
integration proceed. **READY_FOR_GATE_2 = NO** until then.
