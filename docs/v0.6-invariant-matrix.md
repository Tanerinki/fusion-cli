# v0.6 invariant matrix

Every invariant the v0.6 program requires, with the mechanism that enforces it and the test that would fail on a
wrong implementation. Status vocabulary:

- **COVERED** — a deterministic test exists and passes (its exact title is quoted, and a guard test checks it exists).
- **OS-COVERED** — additionally proven by a Windows real-OS integration test (a fake adapter is never evidence for HARD).
- **PLANNED** — specified, not yet implemented in a merged PR. Never claimed as shipped.

A row is only COVERED/OS-COVERED when such a test exists; a comment is never coverage. This document fills in PR by
PR; at PR A only the pure contracts are COVERED.

### Release-readiness of the remaining PLANNED rows (audit)

Every row not marked COVERED/OS-COVERED above is one of the following. None is a downgraded requirement — each stays
listed as not-shipped with its real reason and route to closure.

- **Gated on maintainer elevation (Gate #1).** `ALLOWLIST network egress enforced (deny others)` — applying the WFP rules
  needs a one-time administrator step; the non-elevated side (deterministic plan construction, SID scoping, fail-closed
  posture) is COVERED in D5. DENY_ALL egress itself is already OS-COVERED (no network capability). This is not a
  substrate gap; it is the elevation gate the program defines.
- **OS-live strengthening (maintainer-run, not CI).** `dedicated SSH/browser credential-file canary read denied` and
  `reparse point / junction / \\?\ / UNC escape denied` — the OS token model already denies every ungranted read
  (OS-COVERED: primary/sibling/credential/journal/delivery), and the credential sentinel is proven not to reach output
  (OS-COVERED). These two rows are additional live canaries that exercise a specific credential path and a specific
  path-escape shape against real OS denial; they are maintainer-run like the rest of section B and remain open until run.
- **Covered in parts; unified proof pending.** `injected credential sentinel never reaches candidate output/Delivery/logs`
  — output is OS-COVERED (live contamination), recorded artifacts/logs are redacted (`events` M6: "M6 JSON artifacts
  redact known secrets and refuse raw transcript/env shapes"), and a Delivery is built only from the validated
  `changeSet` (never from provider stdout). A single injected-sentinel end-to-end contamination test tying the three
  sinks together is the remaining strengthening.
- **Finer granularity than shipped reuse (follow-up).** `completed verification-mesh node not repeated` and
  `replay produces identical derived state (generic) — per-workflow reducers` — I7 reuses at the CANDIDATE boundary, so a
  resumed run does not re-run a completed candidate's provider turn; it does deterministically re-run that candidate's
  (cheap, host-controlled) evaluation/mesh from the reused change set. Per-mesh-node memoization and per-workflow replay
  reducers would avoid even that re-run. They are not release-critical (no expensive provider turn is repeated) and are
  deferred; generic deterministic replay is COVERED in A5.

### D6. Durable tournament candidate-result reuse (PR I7)

A tournament candidate's expensive provider generation is persisted durably the moment it produces a validatable change,
so when the SAME run is resumed after a crash it REUSES the completed candidate at the generation boundary instead of
re-running its provider turn (§13, §15). The store is keyed by the durable RUN identity (not the contract): two
independent `fusion build` invocations — even of the identical task — never share candidates, so a fresh run always
generates its own; only a resume that re-adopts the interrupted run's id reuses. Reuse is at the generation boundary
only: evaluation, experiments, verification mesh and selection re-run identically from the reused `changeSet`, so a
resumed run reaches the SAME v0.5 decision as an uninterrupted one. A torn, tampered, foreign or non-revalidating entry
is ignored (the candidate is simply re-run) — fail safe, never wrong. A security-violating or human-gate-halting
candidate is never persisted (it halts before the persist point).

**Honest scope.** The reuse MECHANISM, its crash-safety across a real process boundary, and reuse through the real build
entry point are covered below. What is NOT yet built is a `fusion build` CLI flow that automatically detects an
interrupted prior run and resumes it under its id — so in production the persisted candidates are reused when a run is
resumed under its run id, which no top-level command yet triggers on its own. That CLI resume flow is the documented
follow-up (tracked with the human-gate resume, §14); it is not claimed as shipped.

### D7. Exact human-gate resume across restart (PR I8)

When a run stops for a human, the exact object the human must approve — the work's task DIGEST, the gate reason and the
structured decision request — is captured as a bounded canonical object, hashed, and persisted with the gate as a
durable `humanGateRequired` milestone (§14). The gate is recorded as a PENDING milestone with **no** terminal record and
the lease is released, so the run reconstructs as awaiting a human (INTERRUPTED) — it is never falsely COMPLETED, which is
the bug this closes (a `HUMAN_GATE_REQUIRED` run previously wrote `runCompleted`). On resume — including a fresh process —
`reconstructRun` re-presents PRECISELY that gate; a resume whose re-derived object hashes differently (a changed task,
reason or decision) is refused as a security stop (`assertHumanGateUnchanged`), so a human can never approve one thing
while Fusion proceeds with another. The object binds the WORK, not the ephemeral run id.

**Honest scope.** The gate's durable survival, its exact re-presentation across a real process boundary, and the
object/hash binding that refuses drift are covered below. As with D6, no top-level command yet re-adopts an interrupted
run to continue past the gate automatically; the binding is the guarantee that when such a resume runs, it approves
exactly the recorded object. That CLI resume/approve flow is the documented follow-up, not claimed as shipped.

### D8. ProcessSupervisor → AppContainer launch wiring (PR I10 — deterministic + maintainer-live; real provider is Gate #2)

The production launch path is now routed through the sandbox: when a `ProcessSpec` carries a `sandbox`, `ProcessSupervisor.start`
spawns the native launcher (which runs the target inside a no-capability AppContainer, applies the manifest grants and
minimized env, and bridges stdio, exiting with the child's exit code) instead of the target directly. All of the
supervisor's streaming / timeout / cancel / kill machinery therefore operates unchanged, and killing the launcher closes
its kill-on-close Job so the whole sandboxed tree dies. Fail-closed is structural: an unavailable HARD backend makes the
supervisor REFUSE to start — the target is never run unsandboxed. `prepareSandboxLaunch` writes the run spec (via the
audited `runSpecDocument`) and `providerRunSpec` maps a provider's capability manifest + minimized environment to it.

The deterministic proofs drive the SAME production `ProcessSupervisor.start` sandbox branch with a FAKE launcher binary
(no real AppContainer); the real-OS confinement is proven by the maintainer-live row (real launcher, fake provider child)
and by the existing live provider-sandbox suite (D4). NO real provider, credentials, quota or model call is involved —
that is Gate #2 (§73), unchanged and still gated.
