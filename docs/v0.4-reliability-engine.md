# v0.4 — the reliability engine

**Status: implemented; the real-provider live acceptance is PENDING.** Not released; the package stays at 0.3.0 until the
v0.4 live acceptance ([L1–L5](#live-acceptance-l1l5--by-the-maintainer-from-a-normal-powershell-window)) passes on the
maintainer's machine. This document is the design as built (see [Delivery plan](#delivery-plan)).

v0.4 does not add agents. It makes **silently-wrong success much harder**. Fusion now distinguishes what a model
*claimed*, what Fusion *observed*, what its deterministic evidence *supports* or *contradicts*, what remains *unknown*, and
whether that is strong enough to permit a delivery. It prefers an honest **UNVERIFIED** over a confident, unsupported
success.

**Models propose. Fusion observes and decides what the evidence supports. Humans approve.** Nothing in v0.4 gives a model
more authority, a wider view, a write, a network path, a budget increase or a way past a human gate.

## The Evidence Graph (`src/core/evidence/graph.ts`)

A host-owned, bounded graph of **claims** and **evidence**.

- **Claim**: a stable id, a kind (`task`, `finding`, `hypothesis`, `diagnosis`, `rootCause`, `fixEffect`,
  `counterexample`), its origin (who proposed it), a safe reference to the turn or packet, a subject, the bounded statement,
  the host-checked files it rests on, and optionally the claim it challenges.
- **Evidence**: which claim, its **source**, its relation (`supports`, `contradicts`, `neutral`), a safe label, a bounded
  detail, the **basis** it was observed against (for freshness), and its order.
- Sources and their fixed authority:

| Authority | Sources |
| --- | --- |
| deterministic (Fusion executed or observed it) | `verification` (checks on the change), `reproduction` (the same checks on the unchanged baseline), `fileCheck` (a file check on the shared copy), `diff` (observed changed paths), `protection` (protected-material state) |
| citation | `citation`: the named file exists and was shared — nothing more |
| model (an opinion) | `investigator`, `reviewer`, `falsifier`, `lead`, `worker` |
| human (a decision, not evidence of truth) | `human` |

**The status rule** — derived, never set:

1. **CONTRADICTED** when any fresh deterministic evidence contradicts the claim. One failed test of a claim is enough.
2. otherwise **SUPPORTED** when fresh deterministic evidence supports it;
3. otherwise **STALE** when its only deterministic evidence was observed against a state that is no longer current;
4. otherwise **UNVERIFIED** — however many models agree.

Model judgements are recorded and counted: they make a claim *challenged* or show a *model conflict*, and an untested
counterexample stays an open challenge until Fusion's own evidence refutes it. They never move a status. Nothing is
overwritten: the timeline shows claimed → challenged → tested → contradicted. Bounds: 48 claims, 256 evidence items,
400-character statements; when a bound is hit the graph says so and **no claim of an overflowed graph is SUPPORTED** (a
dropped contradiction could hide). The persisted form is versioned (`fusion.evidenceGraph` v1) and validated exactly on
read; a malformed record is refused, never read as a smaller, cleaner one.

## Proof Obligations (`src/core/evidence/obligations.ts`)

Obligations are typed, persisted with their reasons, and evaluated **mechanically from host facts** (`BuildFacts`): Fusion's
own verification of the change, its reproduction run on the unchanged baseline, the changed paths it observed, the
protected-material state, the fresh review it ran, and the statuses of the evidence graph. No model output is an input.

| Obligation | PASS when (Fusion observed) | FAIL when | UNKNOWN when |
| --- | --- | --- | --- |
| `verificationPassed` (regression checks) | every configured confined check ran and passed on the final change | a check failed | none ran, or verification could not start (its refusal) |
| `scopeRespected` | every changed path is in the confirmed scope | a path is outside it, or the run stopped for scope | nothing was applied |
| `protectedUnchanged` | no protected, credential or never-deliverable path changed | one did | nothing was applied |
| `freshReviewClear` (fresh review / falsification) | the required fresh stage ran and left no outstanding finding | it left one | it did not run (no eligible partner, a failed turn) |
| `defectReproduced` (invalid state shown) | a configured check fails on the unchanged baseline | — | every check passes on the baseline, or the baseline run could not happen |
| `reproductionResolved` (corrected state shown) | every baseline-failing check passes after the change | one still fails | nothing was reproduced, or the final run is missing |
| `rootCauseSupported` | the root-cause claim is SUPPORTED | it is CONTRADICTED | it is UNVERIFIED or STALE |
| `alternativesAddressed` | every recorded competing explanation is CONTRADICTED | one is SUPPORTED | one is untested |
| `behaviorPreserved` | every check that passed on the baseline still passes | one now fails | no check passed on the baseline |

**Decision** (from the obligations alone): **BLOCKED** if any failed; **UNVERIFIED** if any is unknown (or the graph
overflowed); **VERIFIED** only if every required obligation passed. Agreement between models never fills a gap.

**Delivery permission** is stricter than the label: never when BLOCKED, never unless every *safety* obligation passed. A
*correctness* gap (for example, Fusion's checks could not reproduce the defect) is prepared only as **UNVERIFIED** — the
human sees exactly which obligation is unknown and why, and decides. At high risk and for security-sensitive work the
correctness obligations *are* safety obligations: no delivery while they are unknown.

## The reliability policy (`src/core/evidence/policy.ts`)

The host classifies a task from facts it already owns — the human's task text, the confirmed scope, the operation, the task
inspector's path classes and the monotonic risk — never from a model reply:

| Class | When | Adds |
| --- | --- | --- |
| `change` | anything else | the three safety obligations only — v0.3's gates, unchanged |
| `bugFix` | fix/bug/crash/regression wording (English and German) | a baseline reproduction run (no model turn), `defectReproduced`, `reproductionResolved`, `rootCauseSupported` |
| `configFix` | the same wording with a configuration-only scope | reproduction; invalid state shown, corrected state shown |
| `refactor` | refactor/rename/restructure wording or operation | reproduction; `behaviorPreserved` |
| sensitive (a flag) | the inspector's security-sensitive or credential path classes, or a credential-handling signal | a fresh falsification, strict tiers |

| Situation | Route |
| --- | --- |
| trivial read-only question | the lead alone (unchanged) |
| normal analysis | the v0.3 adaptive route (unchanged) |
| checking a claim / hard debugging | immutable evidence snapshot → independent hypotheses → Fusion's discriminating checks → falsification → lead diagnosis |
| low-risk narrow change | v0.3's safe build path + the class's obligations + a baseline reproduction for fixes; no committee |
| medium risk fix, any security-sensitive change | + a fresh falsification that must leave no blocker; Lead adjudication; human approval |
| high risk | + strict tiers |
| critical | unchanged: the human gate before any autonomous work |

Classification only ever adds proof: a misread task costs a confined check run or an honest UNVERIFIED label, never a gate.
Runtime or provider failure can raise uncertainty (an obligation becomes UNKNOWN) and never lowers risk.

## Hypothesis isolation and discriminating experiments (read-only)

For a claim check ("is that really a bug?", "is it true that …?"):

1. **Snapshot.** Fusion builds one immutable evidence snapshot — the claim, the question, Fusion's inventory facts for the
   relevant area, the relevant files — and records its SHA-256.
2. **Independent hypotheses.** Two investigators (the proven explorer partner, a fresh session and view copy each) get the
   same snapshot and nothing else: no other report, no transcript, no lead reasoning. Each returns a closed JSON hypothesis
   report with **checks**: a shared file and an exact text it must contain (or lack) if the claim is true.
3. **Comparison (host).** Verdicts are compared; disagreement is recorded as a conflict, never averaged away.
4. **Discriminating experiments (host).** Fusion authorizes and runs the checks itself: only files of the shared (already
   masked and filtered) copy, bounded literal text, at most a few per route. A check whose result matches the prediction
   supports the claim; one that does not contradicts it. Evaluating on the shared copy means a check can never become an
   oracle for a secret value a model could not read. (Models propose checks; Fusion decides whether they run.)
5. **Falsification** (below), then the **lead's diagnosis** with Fusion's results marked as the only execution evidence.
6. **Decision (host):** the claim's status by the graph rule, shown with its tests.

## The Falsifier

A fresh-context stage whose objective is **to break the current conclusion**, not to approve it. It receives only the task
or claim, the conclusion, Fusion's deterministic results (checks, verification, reproduction) and, for a change, the diff and
the obligations with their statuses. Never a worker transcript or the lead's reasoning. It returns counterexamples, missing
evidence, unsupported assumptions, alternative causes and violated obligations — and, in the read-only route, checks Fusion
can run. Its output is untrusted evidence input: Fusion runs its checks; the lead adjudicates its findings (the build route's
existing adjudication, with Fusion's facts overriding the lead as in v0.3). It never mutates anything: the same read-only
posture, view copy and fresh session as the v0.3 Reviewer. Bound: one falsification stage plus at most one correction and
re-falsification (v0.3's review cycle limit).

Its verdict is a model judgement, never agreement Fusion relies on. The route reports what it said — `fresh falsification
(could not break it)` only for a `holds` verdict without objections, otherwise its counterexamples, missing-evidence
objections and a verdict other than `holds` (for example `(2 missing-evidence objections, verdict unclear)`). Counterexamples no
Fusion check refuted and every missing-evidence objection (no file check can settle one) are **open challenges**: shown on the
claim or diagnosis line, handed to the lead to adjudicate, and carried in a fix's handoff. They never change a status: only
Fusion's checks do.

## The diagnosis → fix handoff

When "fix it" refers to a finding a claim check examined (or to a finding of a diagnosis), the change task carries Fusion's
decision about it (`(Fusion's checks of this finding: SUPPORTED — 2 consistent, 0 contradicted)`), and the build receives a
structured **handoff** — host data, validated again at the build: the claim, Fusion's status of it, the checks Fusion ran with
their outcomes, the competing hypotheses of a diagnosis with their statuses, the falsifier's open challenges, the files it rests
on, and its **basis**: a digest of exactly those files as they were in the checkout right after the check.

- The checked finding is a claim of its own in the build's evidence (`finding`), with the claim check's evidence only — its
  checks, observed against that basis, and its open challenges. The build's own root-cause claim (`root-cause`: the defect
  lies within the confirmed scope) carries the build's evidence (fail before, pass after, confined to that scope). A build that
  passes **never promotes the finding**: an UNVERIFIED finding stays UNVERIFIED in the run's record.
- `rootCauseSupported` passes when either claim is SUPPORTED and fails when either is CONTRADICTED. So an UNVERIFIED finding
  does not forbid a fix the build proves itself, and a contradicted one blocks it.
- At build start Fusion digests the same files again. If one changed, the handoff's evidence is **STALE** and cannot satisfy
  `rootCauseSupported` — only the build's own evidence (its fail-before/pass-after reproduction) can. An unrelated edit elsewhere
  keeps it current. (A content digest, not Git's index: a freshly committed repository's index is rewritten by `git status`
  for a moment, which would make a whole-checkout fingerprint flicker.)
- A diagnosis's competing hypotheses become the `alternativesAddressed` obligation: contradicted ones are addressed, untested
  ones are not, a supported one fails it.
- A finding Fusion's own checks **contradicted** is not fixed as stated: Fusion asks what should change instead.

## Observability

A concise end result (the build route):

```text
Evidence:
  reproduced defect ...... PASS          check unit fails on the unchanged baseline
  defect resolved ........ PASS          check unit failed before the change and passes after it
  root cause ............. SUPPORTED
  regression checks ...... PASS
  confirmed scope ........ WITHIN SCOPE
  protected files ........ UNCHANGED
  fresh falsification .... NO BLOCKER
Decision: VERIFIED
```

The run evidence keeps the decision, the obligations with their reasons and the evidence graph (bounded, redacted); the
delivery's manifest binds the event log's digest, so an approval covers exactly that evidence. Conversations stay in memory
as before; only safe counts reach the session metadata.

## Security invariants (unchanged, and re-tested)

Providers never mutate the primary checkout; the Change Author only proposes; the host applies the ChangeSet into a private
candidate; verification is Fusion's own and confined; reviewer and falsifier are read-only; secrets stay masked or withheld;
delivery, approval, checkout and base bindings and the single-use claim are unchanged; retries stay bounded; no force or
bypass flag; no API-key or pay-as-you-go fallback; no commit, push or merge by Fusion; provider posture is validated exactly
at runtime; the Explorer binding stays unvalidated (the validated Muse 1.4.0-R4302.1 Reviewer binding explores and
falsifies in separate contexts, as in v0.3 — nothing broadens its validation).

## Acceptance

### Black box (offline, part of `npm test`)

`test/v04-black-box-acceptance.test.ts` drives Fusion as a user does: a separate process with `main.js`'s wiring and the
REAL Claude and Muse adapters on scripted fake provider binaries. Only what is observable outside counts — the terminal, the
exit code, the workspace's bytes and what each provider process received. The live verdicts (below) are applied to the same
output, so the runner's rules are pinned to what the product really prints.

| | Scenario | What is shown |
| --- | --- | --- |
| A | Simple success | "what does package.json do?" is one lead turn: no snapshot, no hypotheses, no falsifier, no committee |
| B | Hard debug | a diagnosis: two hypotheses on ONE snapshot, running at the same time (a barrier releases only when both are in flight), neither sees the other's conclusion; Fusion's checks contradict one; one diagnosis survives |
| C | False consensus | both investigators support a false claim; the check Fusion derives from the claim's own words contradicts it → CONTRADICTED, never VERIFIED |
| D | Falsifier catch | the candidate passes Fusion's checks; the falsifier (objective FALSIFICATION, Fusion's baseline facts only) finds a missing condition; the lead confirms; one correction; re-falsified clean → VERIFIED (7 of 7) |
| E | Unverifiable | a security-sensitive fix Fusion cannot reproduce → UNVERIFIED, DECISION_REQUIRED, no delivery, files unchanged |
| F | Verified mutation | analysis → claim check → "fix it" carrying the check's evidence → baseline reproduction → fix → VERIFIED (6 of 6); offline never delivered; with `FUSION_DOCKER_LIVE=1` the real confined Docker verification, delivery, explicit approval and exact apply (L5 verdict PASS) |
| G | The live L2–L4 lines, false consensus FORCED | exactly what the live runner types, on the synthetic Home Assistant fixture with the maintainer's posture (the validated Reviewer binding explores); both investigators support the false claim and Fusion's own check overrules them: L2, L3 and L4 PASS; read-only |
| G2 | The live L3 line, the models right | both investigators reject the false claim (the first real run's shape); Fusion's own check contradicts it: the live L3 verdict PASSes without any model error |

The offline oracle (`FUSION_HARNESS_ORACLE`, test harness only) makes the fake confined check pass only while one file
contains one text, so a defect can be reproduced on the unchanged baseline without Docker; the real-Docker F variant runs the
actual `node --test` in the pinned image.

Scenario G found a real defect before any live run: after a diagnosis, "is it true that configuration.yaml already sets
`trusted_proxies`?" was checked as the earlier finding that shares its terms (which it contradicts). A user's own claim is
now checked as stated; it refers back only when it names a finding ("… the trusted_proxies finding …").

### Live acceptance (L1–L5) — by the maintainer, from a normal PowerShell window

```powershell
git -c http.sslBackend=schannel pull --ff-only; npm ci; npm run build; node scripts/v04-live-acceptance.mjs
```

`scripts/v04-live-acceptance.mjs` is never run by CI and must not be run from inside an AI coding tool. It:

- checks the preconditions first, from `fusion --json doctor --probe` (no model turn): the Lead on a subscription lane with
  its runtime attested, the Reviewer on its validated read-only binding (Muse 1.4.0-R4302.1), and the pinned Docker image.
  Anything else stops it, fail-closed, before a model turn is spent;
- runs the real `fusion` shell only on disposable targets under `%TEMP%` (a clone of this checkout; two copies of the
  synthetic Home Assistant Git fixture), removed afterwards unless `--keep`;
- types only its listed lines; every `[y/N]` question is handed to the maintainer — it never answers one, and no input is No;
- keeps the full transcript on the machine (`%TEMP%\fusion-v04-live-<stamp>.txt`); the summary to paste back has no model
  text, and the fixture's planted sentinels must never appear anywhere.

| | Session | PASS when (`scripts/v04-live-verdicts.mjs`) |
| --- | --- | --- |
| L1 | "what does package.json do?" in the clone | `Route: lead only · 1 model turn`, no committee |
| L2 | "why does Home Assistant reject requests from my reverse proxy?" | one snapshot, two isolated hypotheses answered, compared only afterwards; the fixture unchanged |
| L3 | "is it true that configuration.yaml already sets `trusted_proxies`?" (false by construction of the fixture) | the real-provider integration of "deterministic evidence outranks model judgement": one snapshot for two investigators and both real turns answered; Fusion ran its own check and it contradicts the claim; the claim ended CONTRADICTED whatever the investigators concluded (support or reject — both PASS; a supporting provider is refused); and no claim check of the run (L2, L3, L5) accepted anything Fusion's check contradicted. Otherwise FAIL; never REVIEW. `FALSE_CONSENSUS_OBSERVED` and model conclusions refused elsewhere are information |
| L4 | every claim check of L2, L3 and L5 | a fresh falsification ran and was adjudicated — PASS is not agreement: its objections are reported and stay open; FAIL if it failed, no fresh reviewer existed, or a conclusion a falsifier check contradicted was still reported SUPPORTED; REVIEW if there was nothing to break |
| L5 | analysis → "is the trusted_proxies finding really a problem?" → "fix it" → the maintainer's two answers | checked, handoff, invalid state shown, corrected state shown, Decision VERIFIED, applied, and the fixture's own `verify-git` PASS |

`V0_4_LIVE_ACCEPTANCE` is FAIL if a part failed or did not run or a sentinel leaked, REVIEW if a part needs a human look,
else PASS. v0.4.0 is released by the maintainer, only after a complete PASS.

**L3: two guarantees, kept apart.** The *deterministic invariant* — models agreeing on a false claim are overruled by
Fusion's own evidence — is forced in the black box (C and G, scripted false consensus; the claim-check test "C (false
consensus)") and gates every CI run. The *real-provider integration* is L3 live: real independent turns, Fusion's own check,
and a status no model judgement can move. The live acceptance never requires a provider to make a mistake: investigators who
correctly reject the false claim are a PASS (black box G2 pins that on the product's output), and if one supports it, Fusion
must still refuse it.

### The first real run (2026-09-28): reviewed

`V0_4_LIVE_L1: PASS`, `L2: FAIL`, `L3: PASS`, `L4: PASS`, `L5: PASS`, `SENTINELS_SEEN: NONE`, overall FAIL (transcript
`fusion-v04-live-2026-09-28T13-00-57-616Z.txt`, on the maintainer's machine).

**L2 — FAIL, correctly.** Hypothesis h1 answered; h2 failed twice (the bounded repeat):
`provider failure: Muse Exec reported a failed turn. (reason_class=unclassified reason_chars=53 events=other:104,run.model.configured:1,run.lifecycle.started:1,run.terminal.failed:1 max_model_steps=4 prompt_chars=3402 text_chars=0 exit_code=1)`
(95 other events on the repeat). One hypothesis is never treated as two.

- *Established:* Muse itself ended the turn as failed (`run.terminal.failed`, well-formed JSONL, exit 1 afterwards): not a
  transport, spawn, deadline or protocol failure. No text was produced (`text_chars=0`), so Fusion's structured reader was
  never reached: not a structured-output failure. The prompt (3,402 characters) was identical for both attempts and for h1
  apart from the investigator id: no packet difference explains h1 answering and h2 failing.
- *Not established:* whether the step limit was hit. The reason (53 characters — the same length as the v0.3 live
  investigation failure of 2026-09-28, with a different prompt) matched none of Fusion's patterns, and its text is never
  kept; the 104 events were of types Fusion did not name. No context-limit indication either (small prompt, no pattern
  match). **Root cause: UNKNOWN.**
- *A deterministic defect found on the way:* the hypothesis instructions told the investigator to open at most **4** files
  ("every file you open or search spends one [step]") on a binding capped at **4** model steps, leaving no step for the
  answer; the installed Muse runtime tells a model on its last step that the turn will be "force-terminated as failed" if it
  does not answer. v0.3's explorer instruction had the same 4-on-4 budget. Both now allow 3 files (`explorerFiles: 3`),
  pinned against every validated Muse binding's step cap. The step cap itself is part of the validated Reviewer binding
  (`maxModelSteps: 4`) and is not changed; a larger budget would need its own validation.
- *Classification improved:* a failed Muse turn now names every dotted protocol event label (not only `run.*`), reports the
  terminal payload's field names (`terminal_fields=…`, never a value) and, when a payload field holds exactly one of Muse's
  own failure codes (`stepLimit`, `modelError`, …), `muse_code=…` — `stepLimit` classifies the turn as a step limit
  (`turnLimit`). The next failure of this kind will say which it is.

**L3 — PASS, and its semantics made precise.** The investigators rejected the false claim themselves (`0 support, 2
contradict`); Fusion's two checks contradicted it; the claim ended CONTRADICTED. The first review (#26) made the live
verdict require a model's mistake, which would have made a release depend on a provider randomly erring; the maintainer
rejected that, and the verdict now separates the two guarantees (see [Acceptance](#acceptance)). The live verdict is
stricter than the original one in what the integration must show — two answered independent turns and Fusion's own
contradicting check, not only a claim that was not SUPPORTED. Judged again with it, the first run's L3 is **PASS**.

**L4 — PASS, with semantics made explicit.** The falsifier's verdict was `unclear`, with two missing-evidence objections;
its three checks were consistent with the conclusion. The objections were shown as untrusted, but the route said "could not
break it" and they were counted nowhere, not even in a fix's handoff. Now the route reports the verdict and the objections,
and missing-evidence objections are open challenges (see [The Falsifier](#the-falsifier)). They do not change a status. The
L4 verdict also fails if a falsifier check contradicted a conclusion Fusion still reported SUPPORTED.

**L5 — PASS, intended.** The finding's claim check ended UNVERIFIED: both hypotheses' replies broke Fusion's JSON structure,
so no check ran. The build then established its own obligations: regression, scope, protected files, invalid state shown and
corrected state shown — `VERIFIED (5 of 5)`, applied after the maintainer's approval. An UNVERIFIED diagnosis does not forbid
a fix whose build proves itself. But the build's evidence record used the finding's text as its root-cause claim and put the
build's fail-before/pass-after on it, which made the UNVERIFIED finding read as SUPPORTED there. The finding is now a
separate claim that the build never adds to (see [the handoff](#the-diagnosis--fix-handoff)).

## Limits (v0.4)

- Independence is of context, not of model: on the maintainer's machine both investigators and the falsifier are the
  validated Reviewer binding (one model), each in a fresh session and view copy. Correlated model errors are possible; they
  cannot decide a status, because only Fusion's checks do.
- Claim checks need a binding with a proven read-only posture; without one, v0.3's route runs and the claim stays
  UNVERIFIED. The dedicated Explorer binding stays unvalidated.
- Claims Fusion derives checks from are narrow on purpose: one mentioned file, backtick-quoted literals, no negation.
- Hypothesis replies must be one raw JSON object. In the first real run both L5 hypotheses broke that structure; the claim
  stayed UNVERIFIED (never a guess). Their replies are used as untrusted text only.
- A file check tests literal text in one shared file; it is only as relevant as the prediction it tests. Fusion shows the
  prediction next to the result.
- The reproduction reuses the configured confined checks; Fusion does not write new tests. A defect those checks cannot
  see stays *not reproduced* (UNKNOWN), honestly.
- Interface compatibility for refactors is covered only by the configured checks (for example a typecheck command).

## Future (v0.5 / v0.6 candidates)

- Worker-proposed regression tests, verified fail-before/pass-after in confinement.

- Validating a dedicated Explorer binding with its own authorized live probe.
