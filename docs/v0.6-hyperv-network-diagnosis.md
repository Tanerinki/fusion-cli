# v0.6 - Hyper-V network boundary diagnosis (livegate5) + migration plan

**Status: ARCHITECTURE DIAGNOSIS. livegate5 is a GENUINE network-boundary FAILURE, not a harness bug. The current
`internal`-driver + endpoint-VFP-ACL design is REJECTED. `BROKER_ONLY_NETWORK_BOUNDARY = NOT_PROVEN`,
`READY_FOR_GATE_2 = NO`. No live proof was run for this diagnosis; no evaluator weakening.**

## 1. The observation (real hardware, livegate5)

`ACL_APPLIED=YES`, yet the post-ACL worker canaries reported, on the broker/gateway host IP `10.250.37.1`:

| canary | target | result | expected |
| --- | --- | --- | --- |
| brokerWrongPort | 10.250.37.1:47611 | **ALLOWED** | DENIED |
| hostOtherPort | 10.250.37.1:47620 | **ALLOWED** | DENIED |
| directProviderBypass | 10.250.37.1:47630 | **ALLOWED** | DENIED |
| rawSocketBypass | 10.250.37.1:47630 | **ALLOWED** | DENIED |
| dnsGateway | 10.250.37.1:53/udp | **ALLOWED** | DENIED |

Network verdict = **FAIL** (correctly). Cleanup PASS. **Pattern: every failing destination is the host/gateway IP
`10.250.37.1`, just a different port/protocol.** The only "denied" destinations were LAN/Internet - which an internal
network with no off-subnet route denies **structurally**, so the ACL earned **no** credit for them.

## 2. Is this a genuine boundary failure? YES.

The ACL was supposed to deny all egress except TCP->`10.250.37.1:47610`. Every other port on that same host IP stayed
reachable. The endpoint VFP ACL was **not enforced**. This is a real negative result about the architecture, not a
harness defect, and it must not be reinterpreted or evaluated away.

## 3. Exact likely mechanism

- **`internal` is not a supported Windows container network driver.** Microsoft's current driver list
  ([network-drivers-topologies](https://learn.microsoft.com/en-us/virtualization/windowscontainers/container-networking/network-drivers-topologies),
  updated 2025-09) is exactly: **nat, transparent, overlay, l2bridge, l2tunnel**. There is **no `internal` driver**.
  `docker network create -d internal` produced a non-standard **ICS-type** HNS network (Internet Connection Sharing /
  `SharedAccess`), the same family as the host's "Default Switch"/"WSL" ICS networks seen by the host probe.
- **ICS networks are not on the SDN/VFP policy path.** HNS ACL policies are enforced by **VFP** (RuleType `Switch` = VFP
  filtering, vs `Host` = WFP). VFP endpoint-ACL enforcement is the mechanism Microsoft SDN / Kubernetes NetworkPolicy use,
  and it is documented for **l2bridge / l2tunnel / overlay**. An ICS network is driven by the Windows ICS/`SharedAccess`
  service and WinNAT on the host management vNIC; the container endpoint on it is **not** programmed with enforced VFP ACL
  rules.
- **Host/gateway traffic takes the host stack, not the filtered switch port.** `10.250.37.1` is the host's own vNIC
  (the gateway). On an ICS/internal network, container->gateway/host traffic is delivered via the host TCP/IP + ICS path;
  it does not traverse an enforced VFP ACL on the container's switch port. So **all** same-host ports stayed open.
- **`HcnModifyEndpoint` "succeeding" is not enforcement.** The call returned success and the policy was accepted/stored,
  but on an ICS network nothing enforces it. **API success != enforcement success** - exactly the trap this program warned
  about.

## 4. HCN request shape - verified correct (not the cause)

Compared mechanically against `microsoft/hcsshim/hcn`:

| our request | hcsshim | match |
| --- | --- | --- |
| `{ResourceType:"Policy", RequestType:"Update", Settings:{Policies:[...]}}` | `ModifyEndpointSettingRequest{ResourceType EndpointResourceType, RequestType RequestType, Settings}` + `PolicyEndpointRequest{Policies []EndpointPolicy}` | YES |
| `{Type:"ACL", Settings:{Action,Direction,Protocols,RemoteAddresses,RemotePorts,RuleType,Priority}}` | `EndpointPolicy{Type, Settings}` + `AclPolicySetting{Protocols,Action,Direction,LocalAddresses,RemoteAddresses,LocalPorts,RemotePorts,RuleType,Priority}` | YES |
| `Action` Allow/Block; `Direction` Out; `RuleType` Switch; `RequestType` Update | `ActionType` Allow/Block; `DirectionType` In/Out; `RuleType` Host/Switch; `RequestType` Add/Remove/Update/Refresh | YES |

The request shape, enum values, and `RequestTypeUpdate` apply path are all correct. **The failure is the network type,
not the request.** `apply-acl.ps1` (native `HcnModifyEndpoint`) is retained as-is for the supported-driver successor.

## 5. livegate5 pattern analysis (ACL credited with nothing)

- **Changed by the ACL after apply:** nothing on the host IP - every `10.250.37.1` port/protocol stayed ALLOWED.
- **Denied, but pre-existing (topology, not ACL):** LAN (`192.168.178.1:80`) and Internet (`1.1.1.1:443`) - an internal
  network has no route off its subnet, so these are denied with or without the ACL. The ACL must **not** be credited for
  them. (The authoritative evaluator already requires a host positive control to turn a worker timeout into a proven deny,
  so these would be INCOMPLETE, never a credited PASS - but they are irrelevant to the host-port failures above.)
- **Conclusion:** the endpoint VFP ACL produced **zero** enforced denials on this network. Its one allowed destination
  (the broker) was reachable only because everything on that host IP was reachable.

## 6. Is `internal` viable? NO.

`CURRENT_INTERNAL_VFP_ARCHITECTURE = REJECTED`. `internal`/ICS is not a supported, VFP-ACL-bearing Windows container
network; endpoint ACLs are accepted but not enforced, and host/gateway egress bypasses them. Do not keep patching it.

## 7. Recommended next topology + smallest next PoC

**Recommended: `l2bridge` + Hyper-V isolation + endpoint VFP ACL.** l2bridge is Microsoft's SDN/Kubernetes
network-policy driver; container traffic egresses through an **external** Hyper-V switch with VFP on the endpoint, and
HNS ACL policies on the endpoint are the documented, enforced mechanism (Windows Kubernetes NetworkPolicy is implemented
exactly this way). overlay/l2tunnel also carry VFP policy but add VXLAN / Azure-only assumptions; l2bridge is the
smallest supported option.

**Host-impact to review BEFORE any l2bridge live run (it is broader than the ICS PoC):**
- l2bridge binds an **external** vSwitch to a network adapter (`-o com.docker.network.windowsshim.interface=<NIC>`);
  each external-vSwitch network needs its own adapter. On this host, a **dedicated/secondary adapter** (or a disposable
  vEthernet) must be used so the primary NIC is not disrupted. This is a real host change and is a maintainer gate.
- l2bridge is **static IP only** (no DHCP); `--subnet`/`--gateway` must be set. Container egress to the outside needs an
  explicit OutboundNAT policy (we will NOT enable it - the worker must not reach the outside).
- The broker must bind an IP the l2bridge worker can reach (a host endpoint in the worker's compartment / the gateway),
  and the endpoint VFP ACL must allow ONLY `brokerIp:brokerPort`.

**Smallest next PoC (design only; not yet implemented, no live run):**
1. Create a Fusion-owned l2bridge network on a **dedicated** adapter, static subnet, **no** OutboundNAT.
2. Start the worker (Hyper-V isolated) on it; apply the SAME two-rule endpoint VFP ACL (allow TCP broker/32:port; block
   all else) via the SAME native `HcnModifyEndpoint` path (shape already verified).
3. **Effective-policy gate (added now, see below):** after apply, re-query the endpoint; require the two ACL rules to be
   present (`ACL_EFFECTIVE=YES`) before canaries. (Necessary, not sufficient - ICS would even pass this, since the policy
   is stored; only the canaries prove enforcement.)
4. Run the identical A-J canary matrix with host positive controls. The invariant is unchanged: broker ALLOWED; wrong
   port / other host port / host other IP / LAN / Internet / direct provider / raw socket DENIED; gateway DNS DENIED;
   broker route ALLOWED; unauthorized broker destination DENIED.
5. STOP and report; do not integrate before a clean mechanical PASS.

The same requirements and evaluator apply unchanged. No invariant is weakened.

## 8. Evidence additions landed with this diagnosis (bounded; no architecture rewrite)

To make the next run (on l2bridge) self-diagnosing and to distinguish "policy accepted" from "policy enforced", the
harness now, after `HcnModifyEndpoint`:
- re-queries the worker endpoint and writes `effective-endpoint-<RunId>.json` (endpoint id, network id, endpoint IP, and
  the endpoint's Policies after apply), and computes `ACL_EFFECTIVE=YES|NO` from whether the two expected ACL rules are
  present (pure, unit-tested `aclRulesPresent`); if `NO`, the run stops before the authoritative canaries;
- writes `network-facts-<RunId>.json` (docker driver, HNS network Type + Policies, subnet/gateway, host vNIC IP, worker
  endpoint IP, and whether `10.250.37.1` is the host/gateway endpoint) before cleanup.

These are observability only; they do not change the VFP/HCN ACL contents, the network driver, the broker architecture,
the canary semantics, or the evaluator. They carry directly into the l2bridge PoC.
